> 口径：以严谨务实的总工程师口吻作答，先给结论、以数据支撑、坦诚局限，每条回答为「A：中文 / A: 英文」双语对照。

## 〇、开场：项目介绍

A：本项目的核心结论是先讲清楚——我们交付的是一套面向科研场景的可溯源智能体系统，底层以 LangGraph 做多智能体工序编排，而不是传统单向串行的检索增强生成。常规的基线工艺（baseline）是「问题进、一次性检索、一次性生成」，不具备任务级并行与溯源闭环，在跨文档多跳场景下表现为轮数失控、上下文膨胀、结论无据可查。我们反过来引入三层工序：第一层多智能体调研流水线，将问题拆为带依赖的任务图，依赖驱动并发派发、自动补查，报告每条结论挂引用与证据校验状态；第二层 RAG 与多跳检索，向量加 BM25 双路召回经 RRF 融合、再经 Cross-Encoder 精排，跨文档问题以检索-推理循环由模型输出结构化决策来控制迭代终止；第三层底座与观测，单进程 ReAct 主循环、按回合裁剪上下文、全程可靠性包装与全链路审计，配套只读 Dashboard。实测指标上，调研子图共 8 个工序节点，多跳循环硬上限 4 轮，主循环上下文裁剪阈值 40 回合、保留最近 10 回合，LLM 调用连续失败 3 次触发熔断、死信队列重试 3 次，审计事件以 JSONL 为唯一数据源异步落盘，写入失败不影响主流程。

A: The core conclusion must be stated first: what we delivered is a traceable research agent system built on LangGraph for multi-agent orchestration, rather than the conventional unidirectional serial retrieval-augmented generation. The baseline process admits a query, performs a one-shot retrieval and a one-shot generation, with no task-level parallelism and no traceability loop; under cross-document multi-hop conditions this manifests as uncontrolled iteration counts, context overflow, and conclusions lacking citable provenance. We reversed the thinking and introduced a three-tier process: Tier 1, a multi-agent research pipeline that decomposes the query into a dependency-bound task graph, dispatches tasks on a dependency-driven basis with concurrent execution and automatic re-search, and produces a report in which every conclusion carries citations and an evidence-verification status; Tier 2, RAG and multi-hop retrieval where vector and BM25 dual-channel recall are fused by Reciprocal Rank Fusion and then re-ranked by a Cross-Encoder, and cross-document problems are handled by a retrieve-reason loop in which the model emits a structured decision to govern iteration termination; Tier 3, the foundation and observability layer — a single-process ReAct main loop with turn-based context trimming, unified reliability wrapping for all LLM calls, and end-to-end auditing with a read-only dashboard. On measured figures: the research subgraph comprises 8 process nodes, the multi-hop loop has a hard cap of 4 rounds, the main loop trims context at a threshold of 40 turns while retaining the most recent 10, the circuit breaker opens after 3 consecutive LLM failures with the dead-letter queue retrying 3 times, and audit events are persisted asynchronously to JSONL as the single source of truth without blocking the main flow.

## 一、调研流水线追问

**Q1：整体为什么用 LangGraph，不用自己写状态机？**

A：两个硬理由，不是偏好问题。其一，依赖驱动的并发编排 LangGraph 原生支持——任务间存在依赖、依赖满足才派发，用 `Send` 原语是现成机制，自研要自己管线程与锁，等于把编排复杂度转移到业务代码里。其二，StateGraph 让每个节点只改自己关心的状态切片，配合 reducer 天然解决并发写冲突，免加锁。我们评估过自研状态机的方案，结论是工期与正确性风险都高，不划算。

A: Two hard reasons, not preferences. First, dependency-driven concurrent orchestration is natively supported by LangGraph — inter-task dependencies gate dispatch, and the `Send` primitive is an off-the-shelf mechanism; a bespoke solution would require managing threads and locks in-house, shifting orchestration complexity into business code. Second, the StateGraph lets each node mutate only its own state slice, and with reducers concurrent write conflicts are resolved by design without locking. We evaluated a self-built state machine; the conclusion was that schedule and correctness risk were both unacceptably high, so it was not cost-effective.

**Q2：Send 并发具体怎么做？为什么不直接多线程？**

A：Scheduler 每次从状态里挑出依赖已满足且未跑的任务，对每个任务发一条 `Send("researcher", {...})`，LangGraph 运行时并行调度这些分支。并发粒度是「一个任务」而非「一个请求」，单个任务失败独立重试不影响其余，状态更新由运行时单线程顺序合并，无竞态。我们没用多线程，是因为多线程要在业务层自己处理合并与回滚，而运行时托管并发后这部分可靠性由框架保证，不计入我们的缺陷面。

A: The Scheduler selects, at each step, the tasks whose dependencies are satisfied and not yet executed, and emits one `Send("researcher", {...})` per task; the LangGraph runtime schedules these branches in parallel. The concurrency unit is one task, not one request — a single task failure is retried independently without affecting others, and state updates are merged sequentially by the runtime on a single thread, eliminating race conditions. We did not use raw multithreading because that would push merge and rollback logic into the business layer; by delegating concurrency to the runtime, that reliability is guaranteed by the framework and falls outside our defect surface.

**Q3：多 Agent 并发写同一份状态，怎么避免冲突？**

A：靠 StateGraph 的 reducer，不是靠锁。状态里 tasks、sources、evidences、claims 这些被多个 Researcher 并发写的字段，都定义成按 id 合并的 reducer——不是覆盖，是把各自产出的条目按 id 并入同一字典。所以 N 个 Researcher 同时写 evidences，结果是全集合，不会互相覆盖。冲突的边界我们也讲清楚：若两条 evidence id 相同，说明是同一段证据，合并不丢信息；不同来源对同一事实说法不一致，这不靠 reducer 解决，而是交由 Aggregator 的声明支撑状态去标注 conflict，这是确定性的后置校验，不调模型。

A: We rely on the StateGraph reducers, not locks. The fields written concurrently by multiple Researchers — tasks, sources, evidences, claims — are all defined with id-merge reducers, meaning entries are merged into one dictionary by id rather than overwritten. Thus when N Researchers write to evidences concurrently, the result is the full set with no mutual overwrites. The boundary is also explicit: if two evidence entries share an id, they are the same evidence and merging loses no information; inconsistent statements from different sources about the same fact are not resolved by the reducer but flagged as conflict by the Aggregator's claim-support status, a deterministic post-check that does not invoke the model.

**Q4：Plan Gate 是什么？为什么需要它？**

A：它是 Planner 拆完任务图与 Scheduler 派发之间的一道校验闸门。基线工艺里 Planner（LLM）拆出的 DAG 可能结构有环、漏掉 SOP 要求的维度、或比较类任务没有证据祖先，直接派发后面检索全白做。Gate 先做纯规则校验——无环、依赖存在、SOP 覆盖、证据依赖、冗余、粒度——有 HIGH 问题自动修补、最多两轮，末轮接一次 LLM 评审，最后三态裁决：残留 HIGH 即 REJECT，仅 WARNING 带警告放行，皆无则直接放行。三态裁决是规则判定，LLM 只产 issue 列表，不直接裁决。

A: It is a validation gate between the Planner's task-graph decomposition and the Scheduler's dispatch. In the baseline process, the DAG produced by the Planner (an LLM) may contain cycles, miss SOP-required dimensions, or leave comparison-type tasks without evidence ancestors; dispatching directly would waste all downstream retrieval. The Gate first runs deterministic rule checks — acyclicity, dependency existence, SOP coverage, evidence dependency, redundancy, granularity — and auto-repairs HIGH issues for at most two rounds, then a single LLM critique at the final round, and finally a three-state verdict: residual HIGH yields REJECT, WARNING-only yields ALLOW_WITH_WARNINGS, and a clean graph yields ALLOW. The three-state verdict is rule-based; the LLM only produces an issue list and does not decide.

**Q5：Plan Gate 判 REJECT，调研就失败了吗？**

A：不会整体跑飞。REJECT 时不报废，而是换成按 SOP required 维度逐个建最小任务的兜底计划 `build_fallback_plan`，不再调 LLM、直接复检，原因写入 `plan_gate.reject_reasons` 落库，最终由 Compiler 追加进报告开头，告诉用户哪些维度是兜底的、针对性偏弱。所以最坏情况是报告质量降级，不是系统崩溃。关于兜底计划为何弱，可能是 SOP 维度建模粒度本身较粗，也可能是原问题域超出模板覆盖范围，这里我们没法给一个准确结论，后续版本将做 SOP 维度的专项校准。

A: The overall run does not fail. On REJECT we do not discard the work; instead we substitute a fallback plan `build_fallback_plan` that builds minimal tasks per SOP-required dimension without further LLM calls and is re-validated directly. The reasons are written to `plan_gate.reject_reasons` and persisted, and the Compiler appends them at the top of the report so the user knows which dimensions are fallback and thus less targeted. The worst case is therefore a degraded report, not a system crash. As to why the fallback plan is weak, it may be that the SOP dimension granularity is itself coarse, or that the original problem domain exceeds the template's coverage; we cannot give a precise conclusion here, and a dedicated SOP-dimension calibration is planned for a later version.

**Q6：Review 和 Judge 有什么区别？补检索怎么触发？**

A：Review 出的是「问题清单」——哪些声明支撑不足、哪些来源冲突，属描述性输出；Repair 据此局部增删任务；Judge 做的是「裁决」，看修复后是否还有 HIGH 问题，用 `Command` 决定下一步。补检索的触发链是 Review 发现问题 → Repair 加任务 → Judge 路由回 scheduler，不是 Review 直接触发。Judge 的裁决是纯规则，不依赖模型打分，输入为 DAG 状态（是否还有 READY 任务、轮次是否达 max_revisions=2、可用声明数、连续两轮无新证据则强制终止），输出为 verdict 枚举经 Command 路由。

A: Review produces a problem list — which claims are under-supported, which sources conflict — and is descriptive. Repair then adds or removes tasks locally based on that list, and Judge performs the adjudication, checking whether any HIGH issue remains after repair and using `Command` to decide the next step. The re-search trigger chain is Review finds an issue → Repair adds a task → Judge routes back to the scheduler; Review does not trigger it directly. The Judge's decision is purely rule-based and does not rely on model scoring; its inputs are DAG states (remaining READY tasks, whether rounds reached max_revisions=2, count of usable claims, and forced termination after two consecutive rounds with no new evidence), and its output is a verdict enum routed via Command.

**Q7：报告里的引用和「校验状态」怎么保证是真的？**

A：两点，都是确定性校验，不靠模型自评。一是引用编号在 Compiler 出报告前校验——声明的引用标号必须对应实际检索到的来源，对不上的被标出而非编造。二是每个声明带支撑状态，由 Aggregator 根据「这条声明被哪些 evidence 支撑、这些 evidence 间是否冲突」推导，分为已充分支撑、部分支撑、冲突、无支撑。所以每条结论都挂「基于哪些来源、支撑到什么程度」。至于个别跨文档结论仍为 partial 的原因，可能是检索源覆盖度不足，也可能是模型推理波动导致声明-证据链接缺失，这里我们没办法给一个准确的结论，后续工程将做证据链接的专项排查。

A: Two points, both deterministic checks rather than model self-assessment. First, citation numbering is verified before the Compiler emits the report — a claim's citation label must map to an actually retrieved source, and mismatches are flagged rather than fabricated. Second, every claim carries a support status derived by the Aggregator from which evidences support it and whether those evidences conflict, classified as fully supported, partially supported, conflicting, or unsupported. Thus every conclusion is annotated with its sources and the degree of support. As for why some cross-document conclusions remain partial, it may be insufficient source coverage or model-inference fluctuation causing missing claim-evidence links; we cannot give a precise conclusion here, and a dedicated evidence-link audit is planned for later engineering.

## 二、RAG 与多跳检索追问

**Q8：检索管线为什么又是向量又是 BM25，还要 RRF 和 rerank？**

A：各管各的短板，是分层工序而非堆砌。基线工艺里只用向量召回，对具体方法名、指标这类词面精确匹配容易漏；BM25 正好补词面匹配。两者分数量纲不同、不能直接相加，故用 RRF 按排名融合（k=60 为经验值），只看重排位不看重分，比加权求和鲁棒。融合候选再经 Cross-Encoder reranker（bge-reranker-v2-m3）精排一次，把 query 与 doc 拼一起过模型，相关性判断比双塔向量准。实测是「召回广、融合稳、精排准」三层，不是单点优化。

A: Each layer addresses a distinct weakness; this is a layered process, not stacking. The baseline using vector recall alone easily misses exact lexical matches such as specific method names or metrics; BM25 compensates precisely for lexical matching. Their score scales differ and cannot be summed directly, so we fuse by Reciprocal Rank Fusion on rank only (k=60 as an empirical value), which is more robust than weighted summation. The fused candidates are then re-ranked once by a Cross-Encoder reranker (bge-reranker-v2-m3) that scores query and document jointly, yielding more accurate relevance than dual-tower vectors. In practice this is a three-layer scheme of broad recall, stable fusion, and precise re-ranking, not a single-point optimization.

**Q9：跨文档多跳问题怎么处理？为什么不直接多轮检索？**

A：多轮检索的基线工艺有两个病害：轮数不可控、模型易反复查同一缺口。我们把循环改成检索-推理结构，关键升级是让模型输出结构化决策而非只给下一句话。每轮检索后模型返回一个 `RetrievalDecision`，含当前缺口 gap、检索意图 search_intent、实际检索式 next_query、期望证据与停否标记。这样「继续还是停」由程序按固定规则判定，不是模型说了算，可控性从「靠模型自觉」转为「靠规则约束」。

A: The baseline multi-round retrieval suffers two defects: uncontrolled iteration counts and the model's tendency to re-query the same gap repeatedly. We restructured the loop into a retrieve-reason scheme, and the key upgrade is having the model emit a structured decision rather than merely the next sentence. After each retrieval the model returns a `RetrievalDecision` containing the current gap, the search intent, the actual next query, the expected evidence, and a stop flag. Consequently, whether to continue or stop is decided by fixed program rules, not by the model — controllability shifts from model discretion to rule constraint.

**Q10：多跳循环怎么决定停？会不会死循环？**

A：六个停止原因，最高优先级是硬上限 `RAG_MAX_ITERS`（默认 4 轮），绝对不会超。其余靠程序判定：模型标 SUFFICIENT 即停；next_query 与已查重复即停；本轮无新 evidence（按 evidence_id 去重）即停；连续两轮 gap 相同即停——这条专防模型反复提同一缺口；决策非法（说继续却无 next_query）也停。所以是「硬上限 + 多重语义停止条件」双保险。需要坦诚的是，证据增益只按 evidence_id 做集合去重，不做质量打分、不算置信度，这是已知边界。

A: There are six stop conditions, with the hard cap `RAG_MAX_ITERS` (default 4 rounds) at the top priority, so overflow is impossible. The rest are program-determined: stop if the model flags SUFFICIENT; stop if next_query duplicates a previous one; stop if no new evidence arises this round (deduplicated by evidence_id); stop if the gap repeats across two consecutive rounds — this specifically prevents the model from re-raising the same gap; and stop on an illegal decision (continuing without a next_query). It is therefore a double safeguard of hard cap plus multiple semantic stop conditions. To be candid, evidence gain is deduplicated only by evidence_id as a set, with no quality scoring and no confidence metric — this is a known boundary.

**Q11：检索出来的噪声怎么控制？**

A：两道关卡。一是 rerank 阶段 Cross-Encoder 把不相关片段压到后排、取 top-k；二是单轮检索后有过滤——片段自评与充分性门控，相关性低的片段不进上下文。这块属于 RAG 通用能力而非本项目独创，我们接的是现有实现。关于偶发噪声仍漏入上下文的现象，可能是 reranker 阈值设定偏宽，也可能是长尾查询与训练分布偏离，这里我们没办法给一个准确的结论，后续将做阈值与长尾覆盖的专项调优。

A: Two checkpoints. First, at the re-rank stage the Cross-Encoder pushes irrelevant passages to the rear and we take top-k; second, after each single-round retrieval there is a filter — passage self-assessment and a sufficiency gate — so low-relevance passages do not enter the context. This belongs to general RAG capability rather than being our original contribution; we integrate an existing implementation. Regarding the occasional noise that still leaks into context, it may be that the reranker threshold is set too loose, or that long-tail queries deviate from the training distribution; we cannot give a precise conclusion here, and a dedicated tuning of threshold and long-tail coverage is planned.

## 三、基础框架与审计追问

**Q12：主循环为什么用 ReAct？**

A：调研与 RAG 的本质是「思考-调工具-看结果-再思考」，ReAct 这一范式最贴合。实现上主 Agent 是一个 ReAct 节点加一个 tools 节点，`tools_condition` 自动判断本轮是否要调工具，有则走 tools 回来，无则结束。调研流水线与 RAG 都以工具形式挂在这个主循环上，所以它们是「能力」不是「独立系统」，主循环是唯一的荷载传递主干。

A: Research and RAG are inherently "think-call tool-see result-think again", and the ReAct paradigm fits this most closely. In implementation the main agent is one ReAct node plus one tools node, where `tools_condition` automatically determines whether a tool call is needed this round, looping back through tools if so and terminating otherwise. The research pipeline and RAG are both mounted on this main loop as tools, so they are capabilities rather than independent systems, and the main loop is the single load-bearing backbone.

**Q13：长对话上下文怎么控制？不会爆 token 吗？**

A：有回合裁剪，且是「按回合裁剪」不是「简单截断最后 N 条」。每轮结束调用 `trim_context_messages`，触发阈值 40 回合，裁剪时保留最近 10 回合完整上下文，更早的压缩或丢弃。这样上下文长度有上界，不会因对话久就溢出。具体保留多少轮是配置项，我取的是 40 触发、留 10，这个取值是在长链路调研（十几到二十节点、几十次 LLM 调用）下的实测折中，偏保守以避免关键中间结论被过早压缩丢失。

A: There is turn-based trimming, and it is trimming by turn, not a naive truncation of the last N entries. After each round `trim_context_messages` is invoked; the trigger threshold is 40 turns, and on trimming the most recent 10 turns of full context are retained while earlier ones are compressed or discarded. This bounds the context length so it cannot overflow from a long conversation. The retention count is configurable; I set trigger at 40 and keep 10 — a measured trade-off under long-chain research (a dozen to twenty nodes, dozens of LLM calls), biased conservatively to avoid premature loss of key intermediate conclusions.

**Q14：Entity Ledger 是干嘛的？为什么不直接写进 prompt？**

A：它持久化跨回合长期有效的研究状态——全局硬约束（如实验必须对比基线）、已确认实体、未决问题。之所以单独存而非每轮全量塞 prompt，是因为这些是随对话推进会变的长期记忆，全量塞会越攒越长且易丢。Ledger 存在状态里，每轮只抽当前生效的约束注入提示词。字段名 `global_constraints`，本项目装的是科研约束。这相当于把「过程硬约束」从易失的上下文里抽出来做成持久化荷载，避免跨回合传递时退化。

A: It persists the long-lived research state across turns — global hard constraints (e.g., experiments must compare against a baseline), confirmed entities, and open questions. The reason for storing it separately rather than stuffing it into the prompt every round is that these are long-term memories that evolve as the conversation proceeds; full injection would grow without bound and is prone to loss. The Ledger lives in state, and each round only the currently active constraints are extracted and injected. The field is named `global_constraints`, and in this project it holds research constraints. This is effectively lifting the process hard-constraints out of the volatile context into a persistent load, preventing degradation during cross-turn transfer.

**Q15：LLM 调用怎么保证稳定？熔断降级具体怎么做？**

A：所有 LLM 判定类调用走统一包装 `llm_call_with_reliability`。逻辑链是：先查熔断器，开着直接走降级；没开则执行，失败按重试策略重试，连续失败达阈值（默认 3 次）熔断器打开；熔断后尝试用更强模型跑同一逻辑一次，仍失败进死信队列（重试 3 次）后返回降级值（如空列表）。这样单点模型抖动不拖垮整体调研。关于偶发降级导致某任务结论缺失，可能是上游模型服务瞬时抖动，也可能是并发峰值下重试耗尽，这里我们没办法给一个准确的结论，后续将做熔断触发条件的专项日志分析。

A: All LLM decision-class calls go through a unified wrapper `llm_call_with_reliability`. The logic chain is: check the circuit breaker first and take the degraded path if open; if not open, execute, retry per policy on failure, and open the breaker after the consecutive-failure threshold (default 3) is reached; after opening, attempt the same logic once on a stronger model, and on continued failure enqueue to the dead-letter queue (retrying 3 times) and finally return a degraded value (e.g., an empty list). This prevents a single point of model jitter from collapsing the whole research. Regarding occasional degradation causing a missing task conclusion, it may be transient upstream model-service jitter or retry exhaustion under concurrency peaks; we cannot give a precise conclusion here, and a dedicated log analysis of breaker-trigger conditions is planned.

**Q16：审计和 Dashboard 是干嘛的？为什么不影响主流程？**

A：链路长——一次调研可能十几二十节点、几十次 LLM 调用，出问题不好定位，所以做全链路审计。每个节点用 `@audit_node` 装饰，进出各发一条 AuditEvent 写入 JSONL，事件含 run/node/task 层级、耗时、状态、错误。Dashboard 只读，把 JSONL 增量索引到 SQLite，展示节点 DAG、耗时、失败、重试、降级。不影响主流程的原因有两条：一是 emit 永不抛错，写盘失败最多打印 warning，绝不阻断业务；二是 JSONL 异步队列落盘，不占主线程。审计不存 source_texts 正文，只存 id/状态/来源类型，控制体积。

A: The chain is long — one research run may span a dozen to twenty nodes and dozens of LLM calls, making fault localization hard — so we built end-to-end auditing. Each node is decorated with `@audit_node`, emitting one AuditEvent on entry and exit to JSONL, with run/node/task hierarchy, duration, status, and error. The Dashboard is read-only, incrementally indexing JSONL into SQLite to display the node DAG, durations, failures, retries, and degradations. It does not affect the main flow for two reasons: first, emit never throws, so a write failure at most prints a warning and never blocks business; second, JSONL is persisted via an asynchronous queue, off the main thread. The audit does not store source_texts bodies, only ids/status/source types, to control volume.

## 四、压力题 / 边界题

**P1：你的证据去重只按 ID，质量怎么保证？**

A：诚实讲，目前只做集合去重，不做质量打分、不算置信度。质量靠上游 RAG 的 rerank 与片段过滤保证进来的片段本身相关。去重解决的是「同一段证据反复算增益」的问题，不是「证据对不对」的问题；证据对错交给 Aggregator 的声明支撑状态去标注 conflict 与 unsupported，由用户判断。如果要更强，下一步可加 evidence 质量评分，但当前没做，这是明确的工程取舍而非遗漏。

A: To be honest, currently we only do set deduplication, with no quality scoring and no confidence metric. Quality relies on the upstream RAG reranking and passage filtering to ensure ingested passages are themselves relevant. Deduplication solves the problem of "the same evidence repeatedly counting as gain", not "whether the evidence is correct"; correctness is left to the Aggregator's claim-support status, which flags conflict and unsupported for the user to judge. A stronger scheme would add evidence quality scoring, but that is not implemented now — a deliberate engineering trade-off rather than an omission.

**P2：熔断只覆盖判定类调用，节点级 LLM 失败怎么办？**

A：两层叠加，不是一套。RAG 侧判定方法走 `llm_call_with_reliability` 的熔断降级；调研侧节点（planner/researcher/review 等）走 LangGraph 节点级 `RetryPolicy`——llm_retry 3 次、net_retry 2 次，超限节点报错。节点报错会终止该次调研，但错误进审计日志，不静默丢。所以「判定调用」与「节点调用」是两套保护，覆盖不同故障面。关于节点级重试仍失败导致整轮调研中断，可能是该任务依赖的检索源整体不可达，也可能是节点内逻辑对异常输入的容错不足，这里我们没办法给一个准确的结论，后续将做节点级异常输入的专项加固。

A: The protection is layered, not single. RAG-side decision methods use the `llm_call_with_reliability` breaker-degradation; research-side nodes (planner/researcher/review, etc.) use the LangGraph node-level `RetryPolicy` — llm_retry 3 times, net_retry 2 times, erroring the node beyond that. A node error terminates that research run, but the error enters the audit log and is not silently dropped. Thus "decision calls" and "node calls" are two protections covering different failure surfaces. Regarding a whole-run interruption when node-level retries still fail, it may be that the retrieval sources the task depends on are altogether unreachable, or that the node's tolerance to malformed input is insufficient; we cannot give a precise conclusion here, and a dedicated hardening against node-level exceptional inputs is planned.

**P3：这项目和直接用 LangChain 的 Research 类工具什么区别？**

A：两个核心差异。一是 Plan Gate 前置校验加兜底，通用 Research 工具大多直接派发、不做结构化校验，坏的 DAG 会一路跑到底浪费算力；二是结论可溯源，我每个声明带支撑状态与引用校验，通用工具往往只给最终答案不标每条结论的依据。审计 Dashboard 是额外加的观测能力。当然，通用工具生态更全，我是在其之上按科研场景做定制，不是从零重造。

A: Two core differences. First, the Plan Gate pre-validation with fallback: generic Research tools mostly dispatch directly without structured validation, letting a bad DAG run to completion and waste compute; second, conclusion traceability — every claim of mine carries a support status and citation verification, whereas generic tools often return only the final answer without annotating each conclusion's basis. The audit Dashboard is an added observability capability. Of course, generic tools have a fuller ecosystem; we customized on top of them for the research scenario rather than rebuilding from scratch.

**P4：模型把 Plan Gate 反复判 REJECT，兜底计划很弱怎么办？**

A：兜底计划是按 SOP required 维度建的最小任务，确实针对性弱，但这是「最坏降级」不是「常态」。REJECT 仅在确定性校验仍有 HIGH 问题时触发，而 MISSING_FIELD（任务既无 objective 也无 question）才是稳定触发 REJECT 的唯一类型，大部分情况是 WARNING 带警告放行。planner 本身有 SOP 选型与结构约束，拆出非法 DAG 的概率不高。真触发了，报告开头写明哪些是兜底维度，用户能立刻知道。关于个别复杂问题仍反复 REJECT，可能是 SOP 维度与问题域错配，也可能是 Planner 提示词对多约束任务的约束不足，这里我们没办法给一个准确的结论，后续将做 SOP-问题域匹配的专项评估。

A: The fallback plan builds minimal tasks per SOP-required dimension and is indeed less targeted, but it is the worst-case degradation, not the norm. REJECT triggers only when deterministic validation still finds a HIGH issue, and MISSING_FIELD (a task with neither objective nor question) is the only type that stably triggers REJECT; most cases pass with WARNING. The planner itself has SOP selection and structural constraints, so the probability of an illegal DAG is low. When it does trigger, the report header states which dimensions are fallback so the user knows immediately. Regarding a few complex problems still repeatedly hitting REJECT, it may be a mismatch between SOP dimensions and the problem domain, or insufficient constraint in the Planner prompt for multi-constraint tasks; we cannot give a precise conclusion here, and a dedicated SOP-problem-domain matching assessment is planned.

**P5：审计 JSONL 和 SQLite 是两份，一致性怎么保证？**

A：角色分清楚：JSONL 是审计唯一数据源，SQLite 只是 Dashboard 的查询加速索引，由 `AuditIndexer` 增量从 JSONL 读出来建。所以不存在「双写不一致」——SQLite 永远是 JSONL 的派生物，重新索引即对齐。Dashboard 只读不写，不反向改 JSONL。异常终止也能从已有 JSONL 生成 Summary，因为 summarize 是纯函数、不依赖库。这里要坦诚一个边界：索引是增量的，若 JSONL 在索引窗口外被外部截断或轮转，Dashboard 可能短期少显示若干事件，重新索引即恢复，不影响 JSONL 本身完整性。

A: The roles are clear: JSONL is the single source of truth for audit, and SQLite is merely a query-acceleration index for the Dashboard, built incrementally by `AuditIndexer` reading from JSONL. Thus there is no "dual-write inconsistency" — SQLite is always a derivative of JSONL, and re-indexing realigns it. The Dashboard is read-only and never writes back to JSONL. Even on abnormal termination a Summary can be generated from existing JSONL, because summarize is a pure function independent of the database. One boundary to state candidly: indexing is incremental, so if JSONL is externally truncated or rotated outside the index window, the Dashboard may briefly under-display some events; re-indexing restores them without affecting JSONL integrity itself.
