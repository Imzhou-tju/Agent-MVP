## 〇、开场：项目介绍（先背熟这版）

### 30 秒版（电梯陈述）

"我做了一个面向科研场景的可溯源智能体，基于 LangGraph 搭的。核心解决两件事：一是让大模型做文献调研时能拆任务、并发查、自动补查，最后产出带引用和证据校验状态的报告；二是每一条结论都能追到原始来源。整体是主 Agent 跑 ReAct 循环，调研和 RAG 作为工具挂上去。多跳问题用检索-推理循环，让模型输出结构化决策来控制轮数；另外全链路埋了审计日志，有一个只读 Dashboard 看节点耗时和失败降级。"

### 2 分钟版（技术展开，按三条主线讲）

"分三层说。

第一层是调研流水线。问题进来先过 Planner，按 SOP（标准操作流程；本项目指预定义的研究模板，规定调研必须覆盖的维度）拆成带依赖的任务图，再过 Plan Gate（拆任务后的校验闸门）——先做确定性规则校验（PlanValidator，纯规则、不调模型：查结构无环/依赖存在、SOP 覆盖度、比较类任务有无证据祖先、冗余、粒度），有 HIGH 问题（severity=high 的校验问题，如存在环、悬空依赖、必覆盖维度缺失等；残留 HIGH 即判 REJECT）自动修补、最多两轮，末轮接一次 LLM 评审（SemanticPlanCritic，Plan Gate 内唯一的 LLM 组件；输入是任务图 + SOP + 原始问题，输出是 JSON 问题清单，每条带 severity 与 recommended_action），最后三态裁决（ALLOW / ALLOW_WITH_WARNINGS / REJECT）放行或兜底——三态是规则判定（看终态是否还有 HIGH，不调模型；LLM 只产出 issue 列表，不直接裁决）。

放行的任务由 Scheduler 以 LangGraph 的 Send（原语，用于向图中动态派发多个并发分支）做依赖驱动并发派发，Researcher 检索并登记来源、引文与声明；Aggregator 按引文校验推导每条声明的支撑状态（这一步是确定性计算、不调 LLM，基于引文链接与冲突检测推导 supported / partial / conflict / none），Review 出结构化问题（两部分：确定性部分基于支撑状态与 ConflictDetector，LLM 部分输入为原始问题 + 已完成任务 + 当前声明(带 status) + 当前证据(带校验状态)，输出 schema 为 {issues:[{issue_type, description, severity(high/medium/low), target_type(claim/task/global), target_id, recommended_action(add_task/reopen_task/none), required_evidence, priority(1/2), suggested_task{question, task_type, expected_evidence, search_strategy, dependencies}}]}），Repair 局部增删任务，Judge 用 Command（LangGraph 条件路由原语）路由决定回去补查还是成文（Judge 是规则判定、不调 LLM；输入是 DAG 状态——是否还有 READY 任务、轮次是否达 max_revisions=2、可用声明数、连续两轮无新证据则强制终止；输出为 verdict 枚举 CONTINUE_UNFINISHED / REVISE / COMPILE / COMPILE_WITH_LIMITATIONS / ABORT_WITH_LIMITATIONS，经 Command 路由到 scheduler 或 compiler）。报告由 Compiler 校验引用编号后产出。

第二层是 RAG 与多跳。召回走向量加 BM25 双路、RRF 融合（Reciprocal Rank Fusion，按排名而非分数融合），再经 bge-reranker 做 Cross-Encoder 精排（把 query 与 doc 拼一起过模型打相关性分）。跨文档多跳走检索-推理循环：每轮检索后模型输出结构化决策 RetrievalDecision（本项目定义的结构化对象，含 action / gap / search_intent / next_query / expected_evidence / stop_reason）——由证据 ID 去重与缺口重复检测控制迭代终止（是否继续是规则判定 evaluate()，不调 LLM：模型只产出 RetrievalDecision 对象，evaluate 按 evidence_id 去重、next_query 与已查重复、gap 连续两轮相同、达 RAG_MAX_ITERS 硬上限决定停；输出为 (是否继续, 停止原因)），硬上限四轮。

第三层是底座与观测。底层以单进程 ReAct 主循环驱动，按回合裁剪上下文，Entity Ledger（跨回合持久化的研究状态，含全局硬约束 / 已确认实体 / 未决问题）持久化全局硬约束并注入提示词；所有 LLM 调用走统一可靠性包装，失败重试、升级模型、熔断、死信队列降级。全链路以 `@audit_node`（节点级审计埋点装饰器，进入/退出各发一条 AuditEvent）埋点，审计事件落 JSONL，配套只读 Dashboard 观测节点耗时、失败与降级。"

## 一、按简历三条主线的高频追问

### A. 调研流水线（Planner→Researcher→Review→Judge）

**Q1：整体为什么用 LangGraph，不用自己写状态机？**  
答："两个原因。一是依赖驱动的并发编排 LangGraph 原生支持——任务之间有依赖，依赖满足了才派发，这个用 `Send` 原语很自然，自己写要管一堆线程和锁。二是它的 StateGraph 让每个节点只改自己关心的状态切片，配合 reducer 天然解决并发写冲突，我不用自己加锁。"  
追问链：面试官会接着问"reducer 怎么合的" → 见 Q3。  
代码锚点：`graph.py:47-55`（8 个节点）、`graph.py:57-66`（边与 Send 并发）。

**Q2：Send 并发具体怎么做的？为什么不直接多线程？**  
答："Scheduler 节点每次从状态里挑出依赖已满足、还没跑的任务，对每个任务发一个 `Send("researcher", {...})`，LangGraph 会把这些 Send 并行调度。好处是：并发粒度是'一个任务'而不是'一个请求'，失败的任务独立重试不影响其他；而且状态更新是单线程顺序合并的，没有竞态。"  
易错点：别说是"多线程"，LangGraph 的并发是它运行时调度的，不是我起线程。  
代码锚点：`nodes.py:430`（Send 派发）、`graph.py:50`（researcher 挂了网络重试 RetryPolicy）。

**Q3：多 Agent 并发写同一份状态，怎么避免冲突？**  
答："靠 StateGraph 的 reducer。状态里 tasks、sources、evidences、claims 这些会被多个 Researcher 并发写的字段，都定义成按 id 合并的 reducer——不是覆盖，是把各自产出的条目按 id 合进同一个字典。所以 N 个 Researcher 同时往 evidences 里塞，最后是全集合，不会谁覆盖谁。"  
追问链：面试官可能问"如果两条 evidence id 一样但内容不同呢" → 答："id 是来源+片段哈希生成的，相同 id 意味着同一段证据，合并不会丢信息；冲突的是不同来源对同一事实的说法，这个不靠 reducer 解决，靠 Aggregator 的声明支撑状态去标注。"  
代码锚点：`state.py`（merge_tasks / merge_sources / merge_evidences / merge_claims 按 id 合并）。

**Q4：Plan Gate 是什么？为什么需要它？**  
答："它是 Planner 拆完任务图和 Scheduler 派发之间的一道校验闸门。Planner 是 LLM，拆出来的 DAG 可能结构有环、漏了 SOP 要求的维度、或者比较类任务没有证据祖先。如果直接派发，后面检索全白做。所以 Gate 先做纯规则校验——无环、依赖存在、SOP 覆盖、证据依赖、冗余、粒度——有问题自动修补最多两轮，再做一次 LLM 评审，最后三态裁决：有 HIGH 问题就 REJECT，只有 WARNING 就带警告放行，都没问题就直接放行。"  
追问链：①"修补改坏了怎么办" → 答每轮修补后都会重检，且修补上限 MAX_REPAIRS=8、轮数上限 2，控制成本和把 DAG 改坏的风险。②"REJECT 了怎么办" → 见 Q5。  
代码锚点：`nodes.py:303`（PlanGate 实例化）、`plan_validation.py`（纯规则校验）、三态裁决在 `plan_validation.py` 终态判定。

**Q5：Plan Gate 判 REJECT，调研不就失败了？**  
答："不会直接失败。REJECT 时不报废，而是换成按 SOP required 维度逐个建最小任务的兜底计划 `build_fallback_plan`，这个计划不再调 LLM、直接复检。原因写进 `plan_gate.reject_reasons` 落库，最后 Compiler 把它追加进报告开头，告诉用户哪些维度是兜底的、针对性弱。所以最坏情况是报告质量降级，不会整个跑飞。"  
易错点：说清楚"兜底计划针对性弱于模型拆的"，别把它说得和正常计划一样好。  
代码锚点：`nodes.py:313-315`（build_fallback_plan + 复检）。

**Q6：Review 和 Judge 有什么区别？补检索怎么触发的？**  
答："Review 出的是'问题清单'——哪些声明支撑不足、哪些来源冲突，是描述性的。Repair 拿着问题清单局部增删任务（比如补一个对比任务）。Judge 做的是'裁决'——看修复后还有没有 HIGH 问题，用 `Command` 决定下一步：还有未完成任务就回 scheduler 补查，否则去 compiler 成文。所以补检索的触发链是 Review 发现问题 → Repair 加任务 → Judge 路由回 scheduler，不是 Review 直接触发。"  
代码锚点：`nodes.py:62-64`（review→repair→judge 边）、`nodes.py:1261/1294`（Judge 的 Command 路由）。

**Q7：报告里的引用和"校验状态"怎么保证是真的？**  
答："两点。一是引用编号在 Compiler 出报告前做校验——声明的引用标号必须对应实际检索到的来源，对不上的会被标出来而不是编造。二是每个声明带一个支撑状态：由 Aggregator 根据'这条声明被哪些 evidence 支撑、这些 evidence 之间是否冲突'推导出来，分成已充分支撑、部分支撑、冲突、无支撑几类。所以报告里每条结论都挂着'它基于哪些来源、支撑到什么程度'，不是模型自己说可靠就可靠。"  
易错点：别吹"置信度"——代码里 `confidence_score` 已经删了，现在是证据校验状态 + 声明支撑状态计数。  
代码锚点：`nodes.py:1403`（compiler_node）、Aggregator 支撑状态推导在 `nodes.py` aggregator 段。

### B. RAG 与多跳检索

**Q8：检索管线为什么又是向量又是 BM25，还要 RRF 和 rerank？**  
答："各管各的短板。向量召回管语义相似，但关键词精确匹配（比如具体方法名、指标）容易漏；BM25 正好补这个词面匹配。两者分数量纲不同，不能直接加，所以用 RRF 按排名融合——只看重排位不看重分，k=60 是经验值。融合完的候选再用 Cross-Encoder reranker（bge-reranker-v2-m3）精排一次，Cross-Encoder 把 query 和 doc 拼一起过模型，相关性判断比双塔向量准。所以召回广、融合稳、精排准，三层。"  
追问链：①"RRF 为什么不用加权求和" → 答量纲不同、模型分数不可比，RRF 只看排名更鲁棒。②"rerank 本地还是远程" → 答远程 HTTP 调 SiliconFlow 的 bge-reranker，没本地部署。  
代码锚点：`service.py:175-186`（RRF 融合）、`service.py:464`（rerank 调用）。

**Q9：跨文档多跳问题怎么处理的？为什么不直接多轮检索？**  
答："多轮检索的问题是轮数不可控、而且模型容易反复查同一个缺口。所以我把循环改成'检索-推理'结构，但关键升级是让模型输出结构化决策而不是只给下一句话。每轮检索后模型返回一个 `RetrievalDecision`，里面有：当前缺口 gap、下一轮检索意图 search_intent、实际检索式 next_query、期望拿到的证据、以及停不停。这样'继续还是停'由程序按固定规则判定，不是模型说了算，可控。"  
代码锚点：`retrieval_decision.py:57-65`（RetrievalDecision 字段）。

**Q10：多跳循环怎么决定停？会不会死循环？**  
答："六个停止原因，优先级最高的是硬上限 `RAG_MAX_ITERS`（默认 4 轮），绝对不会超。其余靠程序判定：模型说 SUFFICIENT 就停；next_query 和已查过的重复就停；本轮没有新 evidence（按 evidence_id 去重）就停；连续两轮 gap 相同就停——这个专门防模型反复提同一个缺口。决策本身非法（说继续但没给 next_query）也停。所以是'硬上限 + 多重语义停止条件'双保险。"  
易错点：诚实说"证据增益只按 evidence_id 做集合去重，不做质量打分、不算置信度"——这是已知边界，主动说比被问出来好。  
代码锚点：`retrieval_decision.py:26-31`（6 个 STOP 原因）、`retrieval_decision.py:116-162`（去重与 evaluate 判定）。

**Q11：检索出来的噪声怎么控制？**  
答："两道。一是 rerank 阶段 Cross-Encoder 把不相关片段排到后面，取 top-k。二是单轮检索后有过滤——Self-RAG 式的片段自评和 CRAG 式的充分性门控，相关性低的片段不进上下文。不过这块是 RAG 通用能力，不是本项目独创，我接的是现有实现。"  
代码锚点：`service.py` 的 `_critique_docs` / `_crag_gate`（片段过滤与充分性门控）。

### C. 基础框架与审计

**Q12：主循环为什么用 ReAct？**  
答："调研和 RAG 本质上是'思考-调用工具-看结果-再思考'的过程，ReAct 这个范式最贴合。实现上主 Agent 是一个 ReAct 节点加一个 tools 节点，`tools_condition` 自动判断模型这轮有没有要调的工具，有就走 tools 回来，没有就结束。调研流水线和 RAG 都是以工具形式挂在这个主循环上的，所以它们是'能力'不是'独立系统'。"  
代码锚点：`agent.py:225-235`（add_node + tools_condition 条件边）。

**Q13：长对话上下文怎么控制？不会爆 token 吗？**  
答："有回合裁剪。每轮结束后调用 `trim_context_messages`，触发阈值是 40 轮，裁剪时保留最近 10 轮，更早的压缩或丢弃。这样上下文长度有上界，不会因为聊得久就爆。具体保留多少轮是配置项，我设的是 40 触发、留 10。"  
易错点：说清楚是"按回合裁剪"不是"简单截断最后 N 条"，保留的是最近若干轮完整上下文。  
代码锚点：`agent.py:77`（trim_context_messages(trigger_turns=40, keep_turns=10)）。

**Q14：Entity Ledger 是干嘛的？为什么不直接写进 prompt？**  
答："它持久化跨回合长期有效的研究状态——全局硬约束（比如实验必须对比基线）、已确认实体、未决问题。之所以单独存而不是每次塞进 prompt，是因为这些是'随对话推进会变的长期记忆'，直接全量塞 prompt 会越攒越长、而且容易丢。Ledger 存在状态里，每轮只把当前生效的约束抽出来注入提示词。字段叫 `global_constraints`，这里本项目装的是科研约束。"  
追问链：面试官可能问"和记忆/RAG 什么区别" → 答"RAG 是检索外部知识，Ledger 是维护本次调研过程产生的硬性约束和实体，是过程状态不是外部知识"。  
代码锚点：`entity_ledger.py:73-75`（EntityLedger.global_constraints）；注入在 `agent.py` 的 prompt 组装处。

**Q15：LLM 调用怎么保证稳定？熔断降级具体怎么做？**  
答："所有 LLM 判定类调用走一个统一包装 `llm_call_with_reliability`。逻辑是：先查熔断器，开着就直接走降级；没开就执行，失败按重试策略重试，连续失败达到阈值（默认 3 次）熔断器打开；熔断后尝试用更强模型跑一次同一逻辑，还失败就进死信队列，最后返回降级值（比如空列表）。这样单点模型抖动不会拖垮整个调研。"  
追问链：①"升级模型默认开吗" → 答默认关，要 `.env` 配 `RAG_LLM_ESCALATION_MODEL`，否则熔断后直接降级不升级。②"节点级失败怎么办" → 见压力题 P2。  
代码锚点：`reliability.py:191`（llm_call_with_reliability）、`reliability.py:27`（failure_threshold=3）、`reliability.py:76`（DeadLetterQueue，max_attempts=3）。

**Q16：审计和 Dashboard 是干嘛的？为什么不影响主流程？**  
答："这个项目链路长——一个调研可能十几二十个节点、几十次 LLM 调用，出问题不好定位。所以做了全链路审计：每个节点用 `@audit_node` 装饰，进入和退出都发一个 AuditEvent 写进 JSONL，事件里有 run/node/task 层级、耗时、状态、错误信息。Dashboard 是只读的，把 JSONL 增量索引到 SQLite，展示节点 DAG、耗时、失败、重试、降级。之所以不影响主流程，是因为 emit 永远不抛错——审计写盘失败最多打印一条 warning，绝不阻断业务；而且 JSONL 是异步队列写盘，不占主线程。"  
追问链：①"JSONL 和数据库两份会不会不一致" → 见压力题 P5。②"审计存全文吗" → 答不存 source_texts 正文，只存 id/状态/来源类型，控制体积。  
代码锚点：`audit.py:372`（@audit_node）、`audit.py:275`（emit 不抛错）、`dashboard/indexer.py`（增量索引）、`dashboard/server.py`（只读 API）。

## 二、压力题 / 边界题（面试官挖坑，主动答边界加分）

**P1：你的证据去重只按 ID，质量怎么保证？**  
答："诚实讲，目前只做集合去重，不做质量打分、不算置信度。质量靠上游 RAG 的 rerank 和片段过滤来保证进来的片段本身相关。去重解决的是'同一段证据反复算增益'的问题，不是'证据对不对'的问题。证据对错这部分，靠 Aggregator 的声明支撑状态去标注冲突和无支撑，交给用户判断。如果要更强，下一步可以加 evidence 质量评分，但当前没做。"

**P2：熔断只覆盖判定类调用，节点级 LLM 失败怎么办？**  
答："两层叠加。RAG 侧判定方法走 `llm_call_with_reliability` 的熔断降级；调研侧节点（planner/researcher/review 等）走的是 LangGraph 的节点级 `RetryPolicy`——llm_retry 是 3 次、网络类 net_retry 是 2 次，失败超了节点报错。节点报错会终止该次调研，但错误会进审计日志，不会静默丢。所以'判定调用'和'节点调用'是两套保护，不是只有一套。"

**P3：这项目和直接用 LangChain 的 Research 类工具什么区别？**  
答："两个核心差异。一是 Plan Gate 的前置校验 + 兜底，通用 Research 工具大多直接派发不做结构化校验，坏的 DAG 会一路跑到底；二是结论可溯源——我每个声明都带支撑状态和引用校验，通用工具往往只给最终答案不标注每条结论基于什么。另外审计 Dashboard 是额外加的观测能力。当然，通用工具生态更全，我这是在它之上按科研场景做了定制。"

**P4：模型把 Plan Gate 反复判 REJECT，兜底计划很弱怎么办？**  
答："兜底计划是按 SOP required 维度建的最小任务，确实针对性弱。但这是'最坏降级'不是'常态'——REJECT 只在确定性校验仍有 HIGH 问题时触发，而 MISSING_FIELD（任务既无 objective 也无 question）才是稳定触发 REJECT 的唯一类型，大部分情况是 WARNING 带警告放行。而且 planner 本身有 SOP 选型和结构约束，拆出非法 DAG 的概率不高。真触发了，报告开头会写明哪些是兜底维度，用户能立刻知道。"

**P5：审计 JSONL 和 SQLite 是两份，一致性怎么保证？**  
答："角色分清楚：JSONL 是审计唯一数据源，SQLite 只是 Dashboard 的查询加速索引，由 `AuditIndexer` 增量从 JSONL 读出来建。所以不存在'双写不一致'——SQLite 永远是 JSONL 的派生物，重新索引就能对齐。Dashboard 只读不写，不会反向改 JSONL。异常终止也能从已有 JSONL 生成 Summary，因为 summarize 是纯函数，不依赖库。"

## 四、一句话记忆锚点（每条配一个"钩子"）

- **为什么 LangGraph**：依赖驱动并发 + reducer 免锁，自己写要管线程锁。
- **Plan Gate**：拆完先过规则校验+修补+LLM评审，REJECT 不报废改兜底。
- **Send 并发**：粒度是一个任务，失败独立重试，状态单线程合并。
- **多跳停的条件**：硬上限 4 轮 + 无新证据/缺口重复/模型说够，程序判定不靠模型。
- **RAG 三层**：向量补语义、BM25 补词面、RRF 融排名、rerank 精排。
- **Entity Ledger**：跨回合长期约束存状态里，每轮只抽生效的注入，不全塞 prompt。
- **熔断**：连续失败 3 次开闸 → 升级模型一次 → 死信 → 降级值，绝不拖垮主流程。
- **审计**：@audit_node 写 JSONL，emit 永不抛错，Dashboard 只读派生，不阻断业务。
