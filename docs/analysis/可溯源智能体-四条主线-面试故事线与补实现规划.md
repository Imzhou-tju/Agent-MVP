# 可溯源智能体 四条主线「面试故事线 + 代码对账 + 补实现方案」规划

## 〇、简历描述

**面向科研场景的可溯源智能体** ｜ AI 应用开发（2026.01 - 2026.03）

基于 LangGraph 构建，聚焦文献调研与知识库 RAG，经 MCP 接入学术源并支持结论溯源。

- 搭建 Planner→Researcher→Critic→Judge 流水线，利用 Send API 并发检索、reducer 汇聚证据避免写冲突，经红队评审与条件路由触发补检索，产出带引用与置信度的结构化报告。
- 设计向量 + BM25 双路召回、RRF 融合及 Cross-Encoder rerank；针对跨文档问题实现 retrieve-reason 循环，通过结论压缩控制循环风险，结合 MCP 动态扩展技能并通过 LLM 熔断提升稳定性。

**按代码原文的描述（简历原文保留不动，这一版用于面试对答）**：

- 调研子图有 9 个节点：`planner → scheduler ⇄ researcher → aggregator → review → repair → judge → compiler`。Planner 先按关键词选出研究 SOP 再拆任务 DAG；Scheduler 不调模型，只把依赖已满足的任务用 `Send` 派出去；Researcher 检索并登记来源与引文；Aggregator 按引文校验结果推导声明支撑状态；Review 出结构化问题；Repair 按问题局部增删任务；Judge 裁决继续补查还是成文；Compiler 校验引用编号后出报告。并发写入的字段用按 id 合并的 reducer，不用追加。
- 检索走向量 + BM25 双路召回、RRF 融合（k=60）、远程 bge-reranker 精排；多跳问题用 retrieve→reason 循环，每轮把结论压成 1-2 句存入 evidence_state 控制上下文增长，模型输出结构化检索决策，由证据增益与重复检测决定继续或停止。技能来自目录扫描与懒加载，与 MCP 无关。熔断只覆盖 RAG 侧的判定类调用。

## 二、主线逐条展开

### 主线 0：智能体运行时（公共底座）

**业务背景**：单进程、单用户的本地科研工作台。同一对话进程里同时支撑文献检索、知识库问答、文件与脚本执行、定时任务，且每一步行为留痕可复现。调研流水线与 RAG 都是挂在这个运行时上的工具，不是独立服务。

**故事线**：主循环用 LangGraph 搭成 ReAct 图——`agent` 节点调模型，有 `tool_calls` 就走 `tools` 节点再回 `agent`，否则结束。每轮进 `agent` 前先做上下文裁剪：按完整用户回合分组（一个回合从一条 `HumanMessage` 起，到下一条 `HumanMessage` 前止，中间的 `AIMessage`/`tool_calls`/`ToolMessage` 一并保留），不足 40 回合原样返回，达到 40 只留最后 10 回合；被裁的回合交给 LLM 压成摘要写入 `summary` 字段，原消息用 `RemoveMessage` 删掉。工具分两类：内置工具启动时固定注册；外部技能以目录挂载，启动只扫 `name`/`description`，模型首次调用才读全文。四类行为（发模型的消息、工具调用及入参、工具结果、最终回复）由前台丢内存队列、后台线程按会话写 JSONL。

**可追问点**：①循环靠什么终止（模型不再产出 `tool_calls`，`tools_condition` 自动判断，无自设轮次上限）；②为什么按用户回合而非消息条数裁剪（一次提问带出多轮工具调用，按条数切会把 `AIMessage` 和它对应的 `ToolMessage` 切开）；③技能为什么先读说明书再执行（启动只扫元数据，先读用法再拼命令，避免模型在不知道用法时直接执行）。

**量化**：裁剪调用参数 `trigger_turns=40`、`keep_turns=10`（函数默认值是 8/4，以调用处为准）；摘要提示词要求不超过 150 字；技能元数据缓存 60 秒、正文 LRU 50 条；心跳 10 秒。均为配置常量，无实测。

**代码对账**：图装配 `agent.py:191-201`；裁剪调用 `agent.py:69`；摘要写入 `agent.py:92`，删消息 `agent.py:95`；分组逻辑 `context.py:24-40`；审计埋点 `agent.py:145/162/174`、日志器 `logger.py:85-105`；技能懒加载 `skill_loader.py:23-267`；沙盒路径校验 `sandbox_tools.py:16-22`。

### 主线 1：多智能体调研流水线

**业务背景**：科研调研要对一个问题从多个角度取证并给出可核对来源的结论。单轮检索覆盖不全，且任务间不独立——不先搞清方法原理，就没法做它和另一个方法的对比。本项目把调研拆成带依赖的任务图，由调度器按依赖分批执行。

**故事线**：先用关键词规则选出研究 SOP（FACT/COMPARISON/MECHANISM/SURVEY 四类，只声明该覆盖哪些维度与拆任务的约束，不规定拓扑），Planner 拿到 SOP 后把原始问题拆成 3-6 个研究任务并声明依赖，产出任务 DAG。拆分后过 Plan Gate：确定性的 `PlanValidator` 用同一个 SOP 检查结构合法性与拆分质量（维度是否覆盖、是否过早综合、对比任务有无证据祖先、是否冗余或粒度过粗），有高危问题先局部修补一次，再让 `SemanticPlanCritic` 用一次 LLM 判断计划能否回答用户问题，通过才交给 Scheduler。Scheduler 不调模型，只按依赖挑出 READY 任务用 `Send` 派发，这批跑完再放下一批。Researcher 做混合检索，结果登记成 Source，抽声明时必须同时给引文，返回 `ResearchPacket` 而不直接改全局结论；Aggregator 合并各包并按引文校验结果推导声明支撑状态；Review 出带 target 和 action 的结构化问题；Repair 按问题局部增删任务、不重建整棵树；Judge 裁决继续补查还是成文。

**可追问点**：①为什么用 `Send` 而非 `add_conditional_edges`（后者只能返回单个节点名，无法返回 N 个带各自参数的并发实例）；②为什么不一次性 fan-out（有依赖的任务拿到前序结果才能问出有效问题）；③为什么并发字段要按 id 合并（`operator.add` 是追加，多任务引用同一来源时会登记出重复条目）；④Repair 为什么不重建整棵树（重开会丢掉已经完成的部分）；⑤Judge 为什么不打分（原 `0.5+0.1×证据数−0.2×问题数` 与证据是否通过校验无关）；⑥为什么 SOP 用关键词规则而非 LLM 选型（关键词零成本、零延迟、结果可复现）；⑦为什么 Critic 只一次、Repair 只一次（每多一轮就多一次 LLM 成本和把 DAG 改坏的风险，目标是低成本补一遍，不是修到完美）；⑧为什么 SOP 要前置进 Planner 而不是只在事后校验（拆分这一步全靠 LLM prompt，没有程序化规则，把 SOP 作为 prompt 先验才能从源头约束拆什么；事后校验只能补救已拆错的结果）。

**量化**：单轮 Repair 最多新增 `MAX_REPAIR_TASKS=3`（Review 后的补任务）；`max_revisions` 默认 2；Plan Gate 侧 Critic 最多 1 次 LLM、validator→repair 循环最多 2 轮、单轮补任务上限 `MAX_REPAIRS=8`；SOP 固定 4 类、Critic 单次最多 3 个 issue。无实测吞吐。

`PlanValidator` 是纯 Python 规则检查，不是 agent、不调模型、不读原始问题，只看 DAG 和 SOP（`plan_validation.py:872-916`）：

```python
def validate(self, dag, plan=None):
    issues = []
    issues.extend(PlanSchemaValidator().validate(dag))   # 结构：无环/依赖存在/root 可达
    issues.extend(self._check_coverage(dag, plan))       # SOP 要求的维度有没有任务覆盖
    issues.extend(self._check_evidence_dependency(dag))  # COMPARISON/SYNTHESIS 有无证据祖先
    issues.extend(self._check_redundancy(dag))           # 两个任务目标是否互为子串
    issues.extend(self._check_granularity(dag))          # 一个任务是否塞了 >=3 个并列动作
    return issues
```

Plan Gate 的三态只看「终态有没有 HIGH 级问题」（`plan_validation.py:1084-1090`）：

举例：问题「比较 A 和 B 的方法原理和性能」命中 COMPARISON，SOP 要求 5 个维度（`object_definition`/`method_or_mechanism`/`evaluation_or_comparison`/`evidence`/`synthesis`）。Planner 只拆出 1 个 COMPARISON 任务时，`_check_coverage` 报 4 条 HIGH 的 `MISSING_COVERAGE`，`_check_evidence_dependency` 再报 1 条 HIGH 的 `INSUFFICIENT_EVIDENCE`；repair 按 `capability→task_type` 补任务（COMPARISON 挂 FACT/MECHANISM 做上游，SYNTHESIS 挂事实型任务），补完重检，缺的维度补齐后就是 ALLOW，不再 REJECT。

### 主线 2：证据溯源链

**业务背景**：科研结论必须能回到原始出处，否则无法用于写作与复核。要求每条结论都能指出来自哪个来源、对应哪段原文，且这段原文确实在那个来源里——而不是模型自行生成的。

**故事线**：Researcher 先把每条检索结果登记成 `Source`（`source_id` 由内容哈希生成，并发分支登记同一 URL 会拿到同一个 id），抽声明时必须同时给引文；程序把引文与来源本次检索拿到的正文做定位比对，给 `VERIFIED/PARTIAL/INVALID/UNVERIFIED`。Aggregator 按校验结果推导声明支撑状态（`SUPPORTED/PARTIALLY_SUPPORTED/UNSUPPORTED/CONTRADICTED`），不由模型自评；多条证据之间有冲突时，`ConflictDetector` 按声明的 scope 字段、极性、取值比对，给出 `NO_CONFLICT`/`DIRECT_CONFLICT`/`SCOPE_MISMATCH`/`POTENTIAL_CONFLICT`。Compiler 先把 source_id/evidence_id 编成 `[S1]`/`[E3]` 编号喂模型，成文后由 `CitationVerifier` 校验编号是否存在、证据是否通过校验、证据有没有绑定声明，`UnsupportedClaimDetector` 把 UNSUPPORTED/CONTRADICTED 的声明从正文移除并单列，出问题反馈模型重跑，最后程序追加参考列表与局限说明。

**可追问点**：①为什么 `source_id` 用内容哈希而非自增（Researcher 并发执行，自增会给同一 URL 编出不同 id）；②为什么 PARTIAL 阈值设 0.6（模型复制引文可能带改写，要求完全相等过严）；③为什么声明状态不交模型自评（模型会给自己打高分，支撑状态只取决于证据是否通过校验）；④为什么报告用编号而非 URL（模型抄长 URL 易错，编号由程序映射可机械校验）；⑤`UNVERIFIED` 和 `INVALID` 区别（前者拿不到正文无法判定，后者拿到正文但定位不到）。

**量化**：`PARTIAL_THRESHOLD=0.6`、`MIN_QUOTE_CHARS=8`、`MAX_COMPARE_CHARS=4000`。均为代码常量，无实测准确率。

**代码对账**：来源登记 `evidence.py:51-129`；引文校验 `evidence.py:212-263`；声明状态推导 `claim.py:275-286`；冲突检测 `conflict.py:52-90`；引用校验 `citation.py:191-286`；未支撑拦截 `citation.py:382-440`；Trace `ledger.py:107`；落库 `store.py`（建表 `store.py:85`，写入 `store.py:292`，溯源查询 `store.py:645`）。

### 主线 3：RAG 混合召回与 rerank

**业务背景**：本地知识库问答要求召回不漏、排序准。只走向量在关键词不匹配时召回不全，只走 BM25 在语义不匹配时召回不全，所以两路都召回后融合。

**故事线**：检索先评估查询——只在判定不完整时才多查询扩写、判定复杂多跳时才分解子问题，具体查询直接用原 query。每个查询分别走向量和 BM25 检索，按 RRF（k=60）融合，交给 rerank 精排，再由 LLM 逐片段判相关过滤，最后评估充分性，不足时改写查询补检索一轮。

**可追问点**：①为什么默认不扩写（具体查询被扩写会引入无关词降低匹配分）；②RRF 为什么用排名而非分数（两路分数不可比，排名可归一化）；③BM25 为什么绑子切片再回溯父块（子切片匹配准，父块给完整上下文）；④rerank 失败怎么办（回退向量分数，结果仍可用但排序质量下降）。

**量化**：`RAG_INITIAL_TOP_K=15`、`RAG_TOP_K=4`、`RAG_MAX_ITERS=4`。无实测召回率。

**代码对账**：查询评估 `service.py:78`；BM25 `vector_store.py:216-243`；RRF `service.py:170-181`；rerank `service.py:500-531`；片段过滤 `service.py:183-224`；充分性评估 `service.py:226-306`。

### 主线 4：多跳检索循环与决策机制

**业务背景**：跨文档问题需先查 A 才能确定下一步查 B，单轮检索覆盖不到。循环检索的问题是轮数不可控、上下文随轮次累积，以及模型可能反复提同一个检索式或同一个缺口而不收敛。

**故事线**：循环体是「检索一轮 → 结果压成 1-2 句带来源的结论存入 evidence_state → 推理输出结构化 `RetrievalDecision` → 程序判定继续还是停止」。模型不再只返回一个 next_query，而是给出 `RetrievalDecision`（action/gap/search_intent/next_query/expected_evidence/stop_reason），继续与否由程序按固定顺序判定：达 `RAG_MAX_ITERS` 上限停、无新证据停、取决策、校验、继续或停止。LLM 调用统一走 `llm_call_with_reliability`：主模型重试→失败计一次熔断→升级模型→仍失败入死信队列→返回降级值。

**可追问点**：①为什么改成结构化决策而不是只返回 next_query（只给检索式看不出「为什么还要查」，程序无从判断是否原地打转，带 gap/search_intent/expected_evidence 终止判定才有依据）；②证据增益为什么按 evidence_id 去重（语义增益要模型判、成本高不稳定，ID 去重是确定性的，能挡住换问法召回同一批 chunk）；③gap 重复怎么判（归一化后与上一轮字符串比较，不做语义相似度）；④为什么 `RAG_MAX_ITERS` 放在判定最前（硬上限优先级高于模型给出的 CONTINUE）；⑤决策调用失败怎么办（沿用 `reliable_llm_call` 降级值 STOP/SUFFICIENT，不新增第二套重试）。

**量化**：每轮 1 次决策调用（单轮管线内部最多 4 次判定 + 1 次压缩），`RAG_MAX_ITERS=4` → 单次多跳上限 21 次 LLM 调用，与升级前一致。是调用次数不是耗时。

### 主线 5：监控、审计与 Dashboard（跨主线横向能力）

**业务背景**：调研是长链路多节点流程，出问题时单看最终报告无法定位「哪个节点慢、哪个任务失败、哪次检索没召回、哪次调用走了降级」。需要一次 Run 从 `Run → Node → Task → Retrieval → Evidence → Claim → Citation → Report` 全程留痕，可观察耗时、失败、重试、降级、修补、裁决等关键行为，且不侵入业务决策逻辑。

**故事线**：每个节点产出结构化事件 → 写入 JSONL → 索引进 SQLite → 只读 Dashboard 查询展示。事件由 `@audit_node` 装饰器统一注入 `node_start`/`node_end`，节点内部按业务产出各自的事件；Run 结束后由 `summarize` 纯函数从事件流聚合出 Run Summary。

**可追问点**：①为什么 JSONL 是审计主源、SQLite 只做索引（JSONL 是唯一原始审计数据，与业务库分离；SQLite 索引删掉可重建，只给 Dashboard 查询加速，不是第二套业务状态源）；②为什么 metadata 只放摘要不放 Prompt/正文（审计要可聚合、可追踪的「数量/状态/id/短原因」，全文会膨胀且泄露内容，原文在业务库 `store.load_claim_chain`）；③为什么 `emit` 永不抛错（审计是旁路，不能因记录失败中断调研主流程）；④为什么节点异常记 FAILED 后原样抛出（埋点只观察不改行为，异常交回 `RetryPolicy` 决定是否重试）。

**量化**：`AuditEvent` 12 字段；metadata 单值 500 字符截断、error 200 字符；Dashboard 默认 `127.0.0.1:8765`。均为配置常量，无实测。
