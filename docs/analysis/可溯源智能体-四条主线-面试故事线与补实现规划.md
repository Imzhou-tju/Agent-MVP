## 二、主线逐条展开

### 主线 0：智能体运行时（公共底座）

**业务背景**：单进程、单用户的本地科研工作台。同一对话进程里同时支撑文献检索、知识库问答、文件与脚本执行、定时任务，且每一步行为留痕可复现。调研流水线与 RAG 都是挂在这个运行时上的工具，不是独立服务。

**故事线**：主循环用 LangGraph 搭成最小 ReAct 图——`agent` 节点调模型，有 `tool_calls` 就走 `tools` 节点再回 `agent`，否则结束。每轮进 `agent` 前先做上下文裁剪：按完整用户回合分组，不足 40 回合不动，达到 40 只留最后 10 回合，被裁的回合交给 LLM 压成摘要写入 `summary` 字段，原消息用 `RemoveMessage` 删掉。工具分两类：内置工具启动时固定注册；外部技能以目录挂载，启动只扫 `name`/`description`，模型首次调用才读全文。四类行为（发模型的消息、工具调用及入参、工具结果、最终回复）由前台丢内存队列、后台线程按会话写 JSONL。

**可追问点**：①循环靠什么终止（模型不再产出 `tool_calls`，无自设轮次上限）；②为什么按用户回合而非消息条数裁剪（一次提问带出多轮工具调用，按条数切会把 assistant 和它对应的 tool 结果切开）；③技能为什么先 `help` 再 `run`（启动只扫元数据，先读说明再拼命令，减少模型凭猜测执行）。

**量化**：裁剪 `trigger_turns=40`、`keep_turns=10`；摘要提示词要求 ≤150 字；技能元数据缓存 60 秒、正文 LRU 50 条；心跳 10 秒。均为配置常量，无实测。

**代码对账**：图装配 `agent.py:186-201`；回合裁剪 `context.py:12-56`；摘要与删消息 `agent.py:75-94`；审计埋点 `agent.py:145/162/174`、日志器 `logger.py:36-107`；技能懒加载 `skill_loader.py:23-267`；沙盒路径校验 `sandbox_tools.py:10-25`。

### 主线 1：多智能体调研流水线

**业务背景**：科研调研要对一个问题从多个角度取证并给出可核对来源的结论。单轮检索覆盖不全，且任务间不独立——不先搞清方法原理，就没法做它和另一个方法的对比。本项目把调研拆成带依赖的任务图，由调度器按依赖分批执行。

**故事线**：先用关键词规则选出研究 SOP（FACT/COMPARISON/MECHANISM/SURVEY 四类，只声明该覆盖哪些维度 + 拆任务的生成约束，不规定拓扑），Planner 拿到 SOP 后把原始问题拆成 3-6 个研究任务并声明依赖，产出带依赖的任务 DAG——SOP 是拆分的前置先验，不是事后校验。拆分后过一道 Plan Gate 质量闸门：确定性的 PlanValidator 用同一个 SOP 检查结构合法性与拆分质量（维度是否覆盖、是否过早综合、对比任务有无证据祖先、是否冗余或粒度过粗），有高危问题先局部修补一次，再让 Critic 用一次 LLM 判断「计划能否合理回答用户问题」，通过才交给 Scheduler。Scheduler 不调模型，只按依赖挑 READY 任务用 `Send` 派发，这批跑完再放下一批。每个 Researcher 做混合检索，结果登记成 Source，抽 claim 时必须同时给 quote，返回 `ResearchPacket` 而非直接改全局结论；Aggregator 合并各包并按证据校验结果推导 Claim 支撑状态；Review 出带 target 和 suggested_action 的结构化问题；Repair 按问题局部增删任务、不重建整棵树；Judge 只看两件事——还有没有可执行任务、有没有通过校验的可用声明。

**可追问点**：①为什么 `Send` 而非 `add_conditional_edges`（后者只能返回单个节点名，无法返回 N 个带各自参数的并发实例）；②为什么不一次性 fan-out（有依赖的任务拿到前序结果才能问出有效问题）；③为什么并发字段要按 id 合并 reducer（`operator.add` 追加会让多任务引用同一来源时登记出重复条目）；④Repair 为什么不重建整棵树（重开会丢已完成部分）；⑤Judge 为什么不打分（原 `0.5+0.1×证据数−0.2×问题数` 与证据是否通过校验无关）；⑥为什么 SOP 用关键词规则而非 LLM 选型（低歧义分发，关键词零成本零延迟可复现）；⑦为什么 Critic 只一次、Repair 只一次（每多一轮就多一次 LLM 成本和把 DAG 改坏的风险，目标是低成本兜底不是修到完美）；⑧为什么 SOP 要前置进 Planner 而不是只在事后校验（拆分这一步全靠 LLM prompt，没有任何程序化规则，把 SOP 作为 prompt 先验喂进去才能从源头约束「拆什么」；事后 Validator 只能补救已拆错的结果，不能避免拆错）。

**量化**：单轮 Repair 最多新增 `MAX_REPAIR_TASKS=3`；`max_revisions` 默认 2；Plan Gate 侧 Critic 最多 1 次 LLM、Repair 最多 1 次、SOP 固定 4 类、Critic 单次最多 3 个 issue。无实测吞吐。

**代码对账**：Planner `nodes.py:142`；SOP 选型 `sop.py:175`；Plan Gate 编排 `plan_validation.py:918`；PlanValidator `plan_validation.py:752`；Critic `plan_validation.py:420`；Scheduler `nodes.py:264`，READY 判定 `dag.py:290`；Researcher `nodes.py:297`；Aggregator `nodes.py:564`；Review `nodes.py:631`；Repair `nodes.py:795`；Judge `nodes.py:897`；语义化 reducer `state.py:84-148`。

### 主线 2：证据溯源链

**业务背景**：科研结论必须能回到原始出处，否则无法用于写作与复核。要求每条结论都能指出来自哪个来源、对应哪段原文，且这段原文确实在那个来源里——而不是模型凭印象写的。

**故事线**：Researcher 先把每条检索结果登记成 `Source`（`source_id` 由内容哈希生成，并发分支登记同一 URL 收敛成同一条），抽 claim 时必须同时给 quote；程序把 quote 与来源本次检索拿到的正文做定位比对，给 `VERIFIED/PARTIAL/INVALID/UNVERIFIED`。Aggregator 按校验结果推导 Claim 支撑状态（`SUPPORTED/PARTIALLY_SUPPORTED/UNSUPPORTED/CONTRADICTED`），不由模型自评；多条证据之间有冲突时，`ConflictDetector` 按 claim 的 scope_fields + polarity + value 给出 `DIRECT_CONFLICT/SCOPE_MISMATCH` 而非靠字符串反转猜。Compiler 先把 source_id/evidence_id 编成 `[S1]/[E3]` 短编号喂模型，成文后由 `CitationVerifier` 校验编号是否存在、证据是否通过校验、可用声明是否都被引用，`UnsupportedClaimDetector` 把 UNSUPPORTED/CONTRADICTED 声明从正文移除并单列警示，出问题反馈模型重跑，最后程序追加参考列表与局限说明。

**可追问点**：①为什么 `source_id` 用内容哈希而非自增（Researcher 并发，自增会给同一 URL 编不同 id）；②为什么 PARTIAL 阈值设 0.6（模型复制引文可能带改写，完全相等过严）；③为什么 Claim 状态不交模型自评（模型会给自己打高分，支撑状态应只取决于证据是否通过校验）；④为什么报告用编号而非 URL（模型抄长 URL 易错，编号由程序映射可机械校验）；⑤`UNVERIFIED` 和 `INVALID` 区别（前者拿不到正文无法判定，后者拿到正文但定位不到）。

**量化**：`PARTIAL_THRESHOLD=0.6`、`MIN_QUOTE_CHARS=8`、`MAX_COMPARE_CHARS=4000`。均为代码常量，无实测准确率。

**代码对账**：Source 与登记表 `evidence.py:51-129`；校验器 `evidence.py:177-263`；Claim 状态推导 `claim.py:127-243`；冲突检测 `conflict.py`；引用校验 `citation.py:54-240`，未支撑拦截 `UnsupportedClaimDetector`；Trace `ledger.py:107`。

**它不做什么（边界）**：校验只比对「本次检索拿到的正文」。网页来源拿到的是搜索摘要而非整页正文，`UNVERIFIED/INVALID` 只说明「在拿到的这段文本里定位不到」，不等于原文里不存在。本地知识库来源带 `chunk_id`，可定位到具体切片。quote 是否真的支持 claim（语义匹配）由模型在抽取阶段完成，程序不判断。

**最简源码**：

**缺口补法**：①quote 只与「本次检索正文」比对→网页来源检索时多取正文（Tavily `include_raw_content`）或对 UNVERIFIED 显式标注；②不校验「quote 是否支持 claim」→加语义一致性判定（模型答是/否，否记为 QUALIFIES 而非 SUPPORTS）；③来源质量无程序化区分→按 `source_type` 给支撑状态加权或报告分列学术/网页来源。

### 主线 3：RAG 混合召回与 rerank

**业务背景**：本地知识库问答要求召回不漏、排序准。单一路召回在关键词或语义不匹配时各有盲区，需双路召回后融合。

**故事线**：检索先评估查询——只在判定不完整时才多查询扩写、判定复杂多跳时才分解子问题，具体查询直接用原 query，避免扩写带偏原意。每个查询分别走向量和 BM25 检索，按 RRF（k=60）融合，交给 rerank 精排，再由 LLM 逐片段判相关过滤，最后评估充分性，不足时改写查询补检索一轮。

**可追问点**：①为什么默认不扩写（具体查询被扩写会引入无关词降低匹配分）；②RRF 为什么用排名而非分数（两路分数不可比，排名可归一化）；③BM25 为什么绑子切片再回溯父块（子切片匹配准，父块给完整上下文）；④rerank 失败怎么办（回退向量分数，结果仍可用但排序质量降）。

**量化**：`RAG_INITIAL_TOP_K=15`、`RAG_TOP_K=4`、`RAG_MAX_ITERS=4`。无实测召回率。

**代码对账**：查询评估 `service.py:78-121`；BM25 `vector_store.py:216-243`；RRF `service.py:170-180`；rerank `:500-530`；片段过滤 `:183-224`；充分性评估 `:226-306`。

### 主线 4：多跳检索循环与 LLM 熔断

**业务背景**：跨文档问题需先查 A 才能确定下一步查 B，单轮检索覆盖不到。循环检索的问题是轮数不可控、上下文随轮次累积。

**故事线**：循环体是「检索一轮 → 结果压缩成 1-2 句带来源的结论存 scratchpad → 推理还缺什么并生成下一子问题」。scratchpad 只存压缩结论不存原文，上下文不随轮次线性膨胀。终止三条件：判定已充分、提不出新子问题、缺口描述连续两轮不变。LLM 调用统一走可靠性包装：主模型重试 2 次→失败计一次熔断→升级模型一次→仍失败入死信队列→返回降级值。

**可追问点**：①为什么 scratchpad 存结论而非原文（原文随轮次累积撑大输入）；②为什么需要「缺口连续不变」条件（前两个条件挡不住模型反复提同一缺口）；③熔断覆盖范围（只覆盖 RAG 侧 4 个判定方法，调研子图节点走 LangGraph `RetryPolicy` 不进熔断器）。

**量化**：单轮 `search_agentic` 最多 3 次判定调用；`search_iterative` 最多 4 轮，加上每轮 1 次压缩与最后 1 次综合，最多 16 次 LLM 调用。是调用次数不是耗时。

**代码对账**：循环主体 `service.py:430-498`；结论压缩 `:313-346`；熔断器 `reliability.py:19-63`；统一包装 `reliability.py:182-239`。
