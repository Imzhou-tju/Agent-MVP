## 〇、简历描述

**面向科研场景的可溯源智能体** ｜ AI 应用开发（2026.01 - 2026.03）

项目概述：基于 LangGraph 构建，聚焦文献调研与知识库 RAG，经 MCP 接入学术源并支持结论溯源。

- 搭建 Planner→Researcher→Critic→Judge 流水线，利用 Send API 并发检索、reducer 汇聚证据避免写冲突，经红队评审与条件路由触发补检索，产出带引用与置信度的结构化报告。
- 设计向量 + BM25 双路召回、RRF 融合及 Cross-Encoder rerank；针对跨文档问题实现 retrieve-reason 循环，通过结论压缩控制循环风险，结合 MCP 动态扩展技能并通过 LLM 熔断提升稳定性。

简历这两条只覆盖上层能力。项目本身是一个智能体运行时，调研流水线与知识库 RAG 都以工具形式挂在它的主循环上，见「二、智能体运行时（公共底座）」。

## 二、智能体运行时（公共底座）

**业务背景**：一个单进程、单用户的本地科研工作台。同一个对话进程里要同时支撑文献检索、本地知识库问答、文件与脚本执行、定时任务提醒，并且要求每一步行为留痕、可复现。调研流水线（`deep_research`）与知识库检索（`search_knowledge_base` / `deep_query_knowledge_base`）都是挂在这个运行时上的工具，不是独立服务。

**故事线**：主循环用 LangGraph 搭成最小 ReAct 图——`agent` 节点调模型，`tools_condition` 判断这次响应里有没有 `tool_calls`，有就走 `tools` 节点执行再回到 `agent`，没有就结束。每轮进入 `agent` 节点时先做上下文裁剪：把消息按完整用户回合分组，不足 40 回合不动，达到 40 回合就只保留最后 10 回合，被裁掉的回合交给 LLM 压成摘要写进 `summary` 字段，同时用 `RemoveMessage` 把这些原消息从状态里删掉。工具分两类：内置工具在启动时固定注册；外部技能以目录形式挂载，启动时只扫 `name` 和 `description`，模型首次调用才读全文。四类行为（发给模型的消息条数、工具调用及入参、工具结果、最终回复）由前台丢进内存队列、后台线程按会话分文件写 JSONL。

**可追问点**：①循环靠什么终止（模型不再产出 `tool_calls`，代码里没有自设轮次上限，收敛交给模型）；②为什么按用户回合裁剪而不是按消息条数（一次用户提问可能带出多轮工具调用，按条数切会把 assistant 消息和它对应的 tool 结果切开，留下没有配对的工具消息）；③摘要里为什么不记用户静态偏好（偏好单独存在 `memory/user_profile.md`，写进摘要会随裁剪丢失）；④技能为什么要先 `help` 再 `run`（启动时只扫元数据，避免把所有说明书塞进提示词；先读说明再拼命令，减少模型凭猜测直接执行）。

**量化**：裁剪阈值 `trigger_turns=40`、保留 `keep_turns=10`；摘要提示词要求不超过 150 字；技能元数据扫描缓存 60 秒、内容缓存 LRU 50 条；心跳检查间隔 10 秒。以上均为配置值与代码常量，无实测数据。

## 三、主线逐条展开

### 主线 1：多智能体深度调研流水线

**业务背景**：科研调研需要对一个问题从多个角度取证，并给出可核对来源的结论。单轮检索覆盖不全，人工逐条核对成本高。而且调研任务之间不是完全独立的：不先搞清一个方法的基本原理，就没法做它和另一个方法的对比。本项目把调研拆成带依赖关系的任务图，由调度器按依赖分批执行。

**故事线**：Planner 把原始问题拆成 3-6 个研究任务并声明依赖关系，交给 Scheduler；Scheduler 不调用模型，只按依赖挑出 READY 的任务用 `Send` 派出去，这批跑完后回到 Scheduler 再放下一批。每个 Researcher 做混合检索，把检索结果登记成 Source，再从结果里抽 claim 和 quote，返回 `ResearchPacket` 而不是直接改全局结论；Aggregator 把各包合并，并按证据校验结果推导每条 Claim 的支撑状态；Review 输出带 target 和 suggested_action 的结构化问题；Repair 按问题局部新增或重开 DAG 里的任务，不重新生成整棵树；Judge 只看两件事——还有没有可执行的任务、有没有通过校验的可用声明——给出 `REVISE` / `COMPILE` / `ABORT_WITH_LIMITATIONS`。

**可追问点**：①为什么用 `Send` 而不是 `add_conditional_edges`（后者只能返回单个节点名，无法返回 N 个带各自参数的并发实例）；②为什么不能像旧版那样一次性 fan-out 全部任务（有依赖的任务拿到前序结果才能问出有效的问题，一次性并发等于让它们各自瞎猜）；③为什么并发写入字段要换成按 id 合并的 reducer（`operator.add` 是追加，多个任务引用同一来源时会登记出重复条目；按 id 合并配合内容哈希生成的 id，能让不同分支登记同一来源时收敛成一条）；④Repair 为什么不重新生成整棵树（重开会丢掉已经完成的部分，且无法定位到具体哪个任务有问题）；⑤Judge 为什么不打分（原实现的 `0.5 + 0.1×证据数 − 0.2×问题数` 与证据是否被校验通过无关，是个没有校准的启发式数值）。

**量化**：无实测数据。可数的上界：单轮 Repair 最多新增 `MAX_REPAIR_TASKS = 3` 个任务；`max_revisions` 默认 2，即最多 2 轮修补；DAG 分批执行时，批次数等于任务依赖链的最长路径长度。

**代码对账**：图装配 `graph.py:47-66`；Planner `nodes.py:121`；Scheduler `nodes.py:217`，READY 判定 `dag.py:151`；Researcher `nodes.py:250`，来源登记 `:301`，原文校验 `:396`；Aggregator `nodes.py:491`，支撑状态推导 `claim.py:247`；Review `nodes.py:547`；Repair `nodes.py:643`，重开与下游失效 `dag.py:172/202`；Judge `nodes.py:712`，三种裁决 `:730/741/748`；Compiler `nodes.py:763`；语义化 reducer `state.py:82-148`。

### 主线 2：证据溯源链

**业务背景**：科研场景的结论必须能回到原始出处，否则无法用于后续写作与复核。要求每一条结论都能指出它来自哪个来源、对应哪段原文，并且这段原文确实在那个来源里——而不是模型凭印象写出来的。

**故事线**：Researcher 先把每条检索结果登记成 `Source`（`source_id` 由内容哈希生成，并发分支登记同一 URL 会收敛成同一条），再让模型抽 claim 时必须同时给出 quote；程序把 quote 拿去和该来源本次检索拿到的正文做定位比对，给出 `VERIFIED / PARTIAL / INVALID / UNVERIFIED`。Aggregator 按证据校验结果推导每条 Claim 的支撑状态（`SUPPORTED / PARTIALLY_SUPPORTED / UNSUPPORTED / CONTRADICTED`），这个状态不由模型自评。Compiler 先把 source_id / evidence_id 编成 `[S1] / [E3]` 短编号喂给模型（模型不需要抄 URL），成文后由 `CitationVerifier` 校验编号是否存在、指向的证据是否通过校验、可用声明是否都被引用；校验出问题时把问题清单反馈给模型重跑一次，最后程序追加参考来源列表与局限说明。

**代码实际保证到哪一步**：

| 环节                    | 是否由代码保证 | 说明                                                                                                                     |
| --------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------- |
| 来源登记且不重复              | 是       | `SourceRegistry.upsert` 按 `url > doi > title+source_type` 去重，`source_id` 为内容哈希（`evidence.py:102`、`evidence.py:38`）     |
| quote 必须能定位回原文        | 是       | `EvidenceVerifier.check`：归一化后完整命中 → VERIFIED；最长公共片段占比 ≥0.6 → PARTIAL；否则 INVALID（`evidence.py:196-244`）                 |
| 证据必须引用已登记来源           | 是       | `source_id` 未在 Source Registry 中 → 直接判 INVALID（`evidence.py:202-203`）                                                  |
| Claim 支撑状态            | 是       | `ClaimGraph.recompute_statuses` 按关联证据的校验状态推导，模型不参与（`claim.py:206-243`）                                                 |
| 报告引用编号真实              | 是       | `CitationVerifier.verify` 解析 `[S1]/[E3]`，编号不在目录内报 `unknown_ref`，证据状态不可引用报 `unverified_evidence`（`citation.py:192-240`） |
| 参考来源列表                | 是       | 由 `SourceCatalog.render_references` 按实际引用到的来源生成，不交给模型（`citation.py:161-184`）                                           |
| 结论回溯到检索式              | 是       | `build_trace` 输出「claim → evidence → source → task → retrieval_query」（`ledger.py:107`）                                  |
| quote 与 claim 的语义是否匹配 | 否       | 校验只做文本定位，不判断"这段原文是否真的支持这句话"，后者由模型在抽取阶段完成                                                                               |

**它不做什么（边界）**：校验只能比对"本次检索拿到的正文"。网页来源拿到的是搜索结果摘要而不是整页正文，所以 `UNVERIFIED` / `INVALID` 只说明"在拿到的这段文本里定位不到"，不等于该说法在原始页面里不存在。本地知识库来源带 `chunk_id`，可以定位到具体切片（`locator = chunk:xxx`）。

**可追问点**：①为什么 `source_id` 用内容哈希而不用自增序号（Researcher 是并发的，自增序号在不同分支里会给同一 URL 编出不同 id，合并后就变成两条）；②为什么 PARTIAL 要设 0.6 这个阈值（模型复制引文时可能带少量改写或截断，完全相等过于严格；0.6 是"大部分内容能定位到"的判据，不是精确值）；③为什么 Claim 状态不交给模型自评（模型会给自己生成的结论打高分，而支撑状态应该只取决于证据有没有通过校验）；④为什么报告里用编号而不是 URL（模型抄长 URL 容易出错或被截断，编号由程序建立映射，成文后能机械校验）；⑤`UNVERIFIED` 和 `INVALID` 有什么区别（前者是拿不到正文无法判定，后者是拿到了正文但定位不到）。

**量化**：`PARTIAL_THRESHOLD = 0.6`、`MIN_QUOTE_CHARS = 8`、比对正文上限 `MAX_COMPARE_CHARS = 4000`、单轮新增任务上限 `MAX_REPAIR_TASKS = 3`。均为代码常量，无实测准确率数据。

### 主线 3：RAG 混合召回与 rerank

**业务背景**：本地知识库问答要求召回不漏、排序准确。单一路召回在关键词不匹配或语义不匹配时各有盲区，需要双路召回后融合。

**故事线**：检索时先评估查询——只在判定为不完整时才做多查询扩写、判定为复杂多跳时才分解为子问题，具体查询直接用原 query 检索，避免扩写把原意带偏。每个查询分别走向量检索和 BM25 检索，两路结果按 RRF（k=60）融合；融合结果交给 rerank 精排；再由 LLM 逐片段判断相关性做过滤，最后评估充分性，不足时改写查询补检索一轮。

**可追问点**：①为什么默认不扩写（具体查询被扩写会引入无关词、降低该查询本身的匹配分）；②RRF 为什么用排名而非分数（两路分数不可比，排名可归一化）；③BM25 为什么绑子切片再回溯父块（子切片匹配更准，父块提供完整上下文）；④rerank 失败怎么办（回退为向量分数，结果仍可用但排序质量下降）。

**量化**：默认参数 `RAG_INITIAL_TOP_K=15`、`RAG_TOP_K=4`、`RAG_MAX_ITERS=4`。无实测召回率或排序指标。

**代码对账**：查询评估 `service.py:78-121`、检索主流程 `:146-181`；BM25 `vector_store.py:216-243`（jieba 分词 + `BM25Okapi`）；RRF 融合 `service.py:170-180`；rerank `:500-530`；片段过滤 `:183-224`；充分性评估与补检索 `:226-306`。

### 主线 4：多跳检索循环与 LLM 熔断

**业务背景**：跨多份文档的问题需要先查到 A 才能确定下一步要查 B，单轮检索无法覆盖。循环检索的问题是轮数不可控、上下文随轮次累积。

**故事线**：循环体是「检索一轮 → 把结果压缩成 1-2 句带来源的结论存入 scratchpad → 推理还缺什么并生成下一子问题」。scratchpad 只存压缩后的结论，不存原始文档片段，因此上下文不随轮次线性膨胀。终止有三个条件：判定为已充分、提不出新子问题、缺口描述连续两轮不变。

**可追问点**：①为什么 scratchpad 存结论而不是原文（原文随轮次累积会撑大输入）；②为什么需要「缺口连续不变」这个条件（前两个条件挡不住模型反复提出同一缺口）；③熔断覆盖范围（只覆盖 RAG 侧的 4 个判定方法，深度调研子图的节点 LLM 调用走的是 LangGraph `RetryPolicy`，不进熔断器）。

**量化**：按代码可数的调用次数——单轮 `search_agentic` 最多 3 次 LLM 判定调用（查询评估、片段过滤、充分性评估）；`search_iterative` 最多 4 轮，加上每轮 1 次结论压缩与最后 1 次综合，最多 16 次 LLM 调用。这是调用次数，不是实测耗时。

**代码对账**：循环主体 `service.py:430-498`；终止条件 `:474-487`；结论压缩 `:313-346`；综合 `:400-428`；熔断器 `reliability.py:19-63`；统一包装 `reliability.py:182-239`；节点重试 `graph.py:38-48`。

3. **来源质量没有程序化区分** ✅ **已解决（`75c873e`）** —— 原状：按 source_type 区分只在报告里人工分列。现已加 `Source.content_type`/`quality`/`retrieval_method`/`retrieved_at` 字段，`evidence.source_quality_of(source)` 规则：学术全文=high、web 全文=medium、web 摘要=low；`SourceRegistry.upsert` 自动落 quality。位置：`evidence.py` 的 `source_quality_of` / `Source` 字段、`nodes.py` 的 Source 构造处。自证：只被网页来源支撑的声明与有学术来源支撑的声明，其证据的 `quality` 档位可区分。

### 主线 3 · RAG 混合召回与 rerank

1. **rerank 依赖远程接口** —— 动作：本地部署 `bge-reranker-v2-m3`，改为进程内调用，保留远程为可选项。位置：`rag/service.py` 的 `rerank`（`:500`）。自证：断开网络后 rerank 仍返回分数。

### 主线 4 · 多跳检索循环与熔断

1. **深度调研节点未纳入熔断** ✅ **已解决（`75c873e`）** —— 原状：子图 planner/researcher/review/compiler 的 LLM 调用走 LangGraph `RetryPolicy`，不进 `reliability.py` 熔断器与死信队列。现已加 `research/reliability.py: reliable_llm_call` + `ReliableLLM`，复用 `rag/reliability` 的 `CircuitBreaker`/`DeadLetterQueue`，把 planner/researcher/review/compiler 各 `llm.invoke` 处换成「重试 → 升级模型 → 熔断 → 死信 → 降级 fallback」包装；语义校验器经 `ReliableLLM` 适配走同一套熔断/死信。位置：`research/reliability.py`、`nodes.py` 各调用点。自证：连续失败 3 次后节点走降级返回值，死信表新增记录。
2. **升级模型默认关闭** —— 动作：在 `.env` 显式配置 `RAG_LLM_ESCALATION_MODEL`。位置：`.env`。自证：主模型失败时日志出现升级模型调用记录。（**仍未解决**：需在配置里显式指定升级模型才生效。）

## 九、Plan Verification & Repair（`research/plan_validation.py`）

在 Planner 生成 DAG 之后补「计划验证」层，回答「DAG 是否真的覆盖用户问题」这类此前无法判断的缺口。不改 Scheduler / Researcher / 检索，复用现有 ResearchPlan / ResearchTask / TaskDAG。

**流程**：

```
执行前：Planner → PlanSchemaValidator → PlanCoverageValidator → SemanticPlanCritic
              → LocalRepair → ValidatedPlan → Scheduler
执行后：Evidence/Claim → EvidenceCoverageValidator → PASS/GAP → LocalRepair Task
```

**新增组件**（`research/plan_validation.py`）：

| 组件 | 类型 | 回答的问题 |
|---|---|---|
| `PlanSchemaValidator` | 确定性 | DAG 结构是否合法（8 项：唯一/依赖存在/无自依赖/无环/type 合法/字段非空/root 可达/依赖能提供输入） |
| `PlanCoverageValidator` | 确定性 | 任务是否覆盖 `required_capabilities`，缺失输出 `MISSING_CAPABILITY` |
| `TaskSuccessCriteriaEvaluator` | 确定性 | 任务结果是否满足结构化完成条件（`PASS/PARTIAL/FAIL`） |
| `EvidenceCoverageValidator` | 确定性 | 最终 Evidence/Claim 是否覆盖关键维度，缺失输出 `COVERAGE_GAP` |
| `SemanticPlanCritic` | LLM | 语义检查（遗漏维度/冗余/粗粒度/不合理依赖），只给局部建议、不重建 DAG |

**关键设计**：
- 能确定性判断的绝不用 LLM：Schema/Coverage/SuccessCriteria/EvidenceCoverage 全部纯代码；只有语义层面的「是否遗漏维度」「任务是否冗余」交给 Critic，且 Critic 异常时静默降级为空。
- local repair：`validate_plan` 编排只做 `add_task`/`remove_task`（删冗余/不可达任务），受 `max_repairs` 上限；达到上限保留现状并输出未解决问题，不因一个局部问题重建整张 DAG。
- 字段向后兼容：`ResearchTask.capabilities/criteria`、`ResearchPlan.required_dimensions/required_capabilities` 均带默认值；旧 dict 经 `from_dict` 白名单过滤，不丢字段不报错。
- 不新增 LangGraph 节点：验证链内联在 `planner_node`（执行前）、`review_node`（执行后），图拓扑不变。

**可追问点**：①为什么「依赖能否提供输入」用 task_type 规则判断而非 LLM（COMPARISON 依赖 FACT/MECHANISM/METHOD 才有意义，反向是错边，规则即可判，不必调模型）；②为什么 Critic 只给局部建议不重建 DAG（重建会丢掉已完成的调研与可追溯性，且无法定位具体问题）；③`required_capabilities` 从哪来（需 Planner 声明或调用方注入，当前尚未从 query 自动推导，是已知局限）。

**仍留的边界（面试勿说满）**：`required_capabilities` 目前靠显式声明，Planner 未自动从问题推导维度；Critic 语义判断依赖 LLM；未做端到端测试。
