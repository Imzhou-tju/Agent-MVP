## 二、智能体运行时（公共底座）

**业务背景**：一个单进程、单用户的本地科研工作台。同一个对话进程里要同时支撑文献检索、本地知识库问答、文件与脚本执行、定时任务提醒，并且要求每一步行为留痕、可复现。调研流水线（`deep_research`）与知识库检索（`search_knowledge_base` / `deep_query_knowledge_base`）都是挂在这个运行时上的工具，不是独立服务。

**故事线**：主循环用 LangGraph 搭成最小 ReAct 图——`agent` 节点调模型，`tools_condition` 判断这次响应里有没有 `tool_calls`，有就走 `tools` 节点执行再回到 `agent`，没有就结束。每轮进入 `agent` 节点时先做上下文裁剪：把消息按完整用户回合分组，不足 40 回合不动，达到 40 回合就只保留最后 10 回合，被裁掉的回合交给 LLM 压成摘要写进 `summary` 字段，同时用 `RemoveMessage` 把这些原消息从状态里删掉。工具分两类：内置工具在启动时固定注册；外部技能以目录形式挂载，启动时只扫 `name` 和 `description`，模型首次调用才读全文。四类行为（发给模型的消息条数、工具调用及入参、工具结果、最终回复）由前台丢进内存队列、后台线程按会话分文件写 JSONL。

**可追问点**：①循环靠什么终止（模型不再产出 `tool_calls`，代码里没有自设轮次上限，收敛交给模型）；②为什么按用户回合裁剪而不是按消息条数（一次用户提问可能带出多轮工具调用，按条数切会把 assistant 消息和它对应的 tool 结果切开，留下没有配对的工具消息）；③摘要里为什么不记用户静态偏好（偏好单独存在 `memory/user_profile.md`，写进摘要会随裁剪丢失）；④技能为什么要先 `help` 再 `run`（启动时只扫元数据，避免把所有说明书塞进提示词；先读说明再拼命令，减少模型凭猜测直接执行）。

**量化**：裁剪阈值 `trigger_turns=40`、保留 `keep_turns=10`；摘要提示词要求不超过 150 字；技能元数据扫描缓存 60 秒、内容缓存 LRU 50 条；心跳检查间隔 10 秒。以上均为配置值与代码常量，无实测数据。

## 三、主线逐条展开

### 主线 1：多智能体深度调研流水线

**业务背景**：科研调研需要对一个问题从多个角度取证，并给出可核对来源的结论。单轮检索覆盖不全，人工逐条核对成本高。本项目把调研拆成固定流水线，由多个角色节点分阶段处理。

**故事线**：Planner 把原始问题拆成 3-6 个子任务，用 `Send` 一次性并发派出 N 个 Researcher；每个 Researcher 做混合检索并从结果中抽 claim 级证据，写入共享 state 的 `evidences`；因为多个 Researcher 并发写同一个字段，该字段声明 `operator.add` reducer，避免互相覆盖。Aggregator 去重后，Critic 以挑刺视角找缺失与矛盾，Revision 按缺失类问题补检索，Judge 依据「是否还有 high 级问题 + 已补轮次」决定进入 Compiler 还是再走一轮。

**可追问点**：①为什么用 `Send` 而不是 `add_conditional_edges`（后者只能返回单个节点名，无法返回 N 个带各自参数的并发实例）；②为什么 `evidences` 必须声明 reducer（N 个 Researcher 并发写同一字段，无 reducer 会互相覆盖）；③Judge 判定读的是谁的结果（读上一轮 Critic 写的 `critic_notes`，不是刚跑完的 Revision 结果）。

**量化**：无实测数据。`max_revisions=2` 时 Revision 节点执行 3 次（首轮无条件 1 次 + 回环 2 次），因为 `revision_count` 从 0 起、Judge 首次必放行。

**代码对账**：图装配 `graph.py:35-60`；Planner fan-out `nodes.py:77`；Researcher `nodes.py:92`；Aggregator `nodes.py:167`；Critic `nodes.py:195`；Revision `nodes.py:244`；Judge `nodes.py:305`、判定式 `:319`；Compiler `nodes.py:347`；reducer `state.py:103`。

**具体做法**：

| 项 | 怎么做的 | 代码位置 |
| --- | --- | --- |
| 并发 fan-out | Planner 返回 `Command(goto=[Send("researcher", {...}) for ...])`，每个 Send 带自己的 sub_task payload | `nodes.py:77-85` |
| 证据合并 | `evidences` 声明 `Annotated[list[dict], operator.add]`，多实例并发写入由 reducer 拼接 | `state.py:103` |
| 证据抽取 | 检索结果去重组装成带编号的文本，LLM 按编号输出 claim + `source_index` + `raw_text` | `nodes.py:120-155` |
| 证据去重 | 按 `claim[:80]` 判重，保留首次出现的那条及其来源 | `nodes.py:177-180` |
| 补充检索词生成 | 只有 `issue_type == "missing_evidence"` 的问题生成检索词，格式为「原问题 + 问题描述」，最多 3 条 | `nodes.py:230-236` |

### 主线 2：证据溯源链

**业务背景**：科研场景的结论必须能回到原始出处，否则无法用于后续写作与复核。要求每一条结论都能指出它来自哪个来源、对应哪段原文。

**故事线**：每条证据在抽取阶段就绑定来源对象（url / title / snippet / 检索词）和原文片段，来源由 LLM 输出的 `source_index` 映射回本次检索结果列表得到；Aggregator 额外建立 claim 到来源列表的映射；Compiler 把「claim + 来源 URL」逐条拼成证据块喂给 LLM 生成报告，并把证据 URL 去重后作为参考来源列表输出。

**代码实际保证到哪一步**：

| 环节 | 是否由代码保证 | 说明 |
| --- | --- | --- |
| 证据带来源结构 | 是 | `nodes.py:144-155` 写入 `source{url,title,snippet,search_query}` |
| 来源映射到真实检索结果 | 是 | `nodes.py:142-143` 用 `source_index` 索引 `unique_results`，越界时 `src = {}`，url 为空字符串且不报错 |
| 原文片段真实存在于来源 | 否 | `raw_text` 由 LLM 在抽取时自行填写（`nodes.py:130` 的示例字段），未与 `source.snippet` 做包含或相似度校验 |
| 报告中的引用来自已检索来源 | 否 | 报告由 `nodes.py:368-383` 的 LLM 自行撰写；无代码比对报告中出现的 URL 是否属于已检索来源集合 |
| claim→来源映射被使用 | 否 | `claim_evidence_map` 在 `nodes.py:181-187` 构造并写入 state，全项目无读取方 |

**可追问点**：①来源 URL 为空时怎么处理（当前不处理，证据照常进入列表）；②`raw_text` 的可靠性（由模型填写，未校验）；③去重键为什么用前 80 字符（代价是前 80 字符相同但来源不同的 claim 会被合并，只保留第一条的来源）。

**量化**：无实测数据。

### 主线 3：RAG 混合召回与 rerank

**业务背景**：本地知识库问答要求召回不漏、排序准确。单一路召回在关键词不匹配或语义不匹配时各有盲区，需要双路召回后融合。

**故事线**：检索时先评估查询——只在判定为不完整时才做多查询扩写、判定为复杂多跳时才分解为子问题，具体查询直接用原 query 检索，避免扩写把原意带偏。每个查询分别走向量检索和 BM25 检索，两路结果按 RRF（k=60）融合；融合结果交给 rerank 精排；再由 LLM 逐片段判断相关性做过滤，最后评估充分性，不足时改写查询补检索一轮。

**可追问点**：①为什么默认不扩写（具体查询被扩写会引入无关词、降低该查询本身的匹配分）；②RRF 为什么用排名而非分数（两路分数不可比，排名可归一化）；③BM25 为什么绑子切片再回溯父块（子切片匹配更准，父块提供完整上下文）；④rerank 失败怎么办（回退为向量分数，结果仍可用但排序质量下降）。

**量化**：默认参数 `RAG_INITIAL_TOP_K=15`、`RAG_TOP_K=4`、`RAG_MAX_ITERS=4`。无实测召回率或排序指标。

**代码对账**：查询评估 `service.py:78-121`、检索主流程 `:146-181`；BM25 `vector_store.py:216-243`（jieba 分词 + `BM25Okapi`）；RRF 融合 `service.py:170-180`；rerank `:500-530`；片段过滤 `:183-224`；充分性评估与补检索 `:226-306`。

**具体做法**：

### 主线 4：多跳检索循环与 LLM 熔断

**业务背景**：跨多份文档的问题需要先查到 A 才能确定下一步要查 B，单轮检索无法覆盖。循环检索的问题是轮数不可控、上下文随轮次累积。

**故事线**：循环体是「检索一轮 → 把结果压缩成 1-2 句带来源的结论存入 scratchpad → 推理还缺什么并生成下一子问题」。scratchpad 只存压缩后的结论，不存原始文档片段，因此上下文不随轮次线性膨胀。终止有三个条件：判定为已充分、提不出新子问题、缺口描述连续两轮不变。

**可追问点**：①为什么 scratchpad 存结论而不是原文（原文随轮次累积会撑大输入）；②为什么需要「缺口连续不变」这个条件（前两个条件挡不住模型反复提出同一缺口）；③熔断覆盖范围（只覆盖 RAG 侧的 4 个判定方法，深度调研子图的节点 LLM 调用走的是 LangGraph `RetryPolicy`，不进熔断器）。

**量化**：按代码可数的调用次数——单轮 `search_agentic` 最多 3 次 LLM 判定调用（查询评估、片段过滤、充分性评估）；`search_iterative` 最多 4 轮，加上每轮 1 次结论压缩与最后 1 次综合，最多 16 次 LLM 调用。这是调用次数，不是实测耗时。

**代码对账**：循环主体 `service.py:430-498`；终止条件 `:474-487`；结论压缩 `:313-346`；综合 `:400-428`；熔断器 `reliability.py:19-63`；统一包装 `reliability.py:182-239`；节点重试 `graph.py:38-48`。

**具体做法**：

| 项 | 怎么做的 | 代码位置 |
| --- | --- | --- |
| 循环上限 | `RAG_MAX_ITERS`，默认 4 | `config.py:58`、`service.py:444` |

## 四、简历表述对账（易被问穿项）

### 1｜聚焦文献调研、面向科研场景

- **代码实际情况**：本地知识库目录 `workspace/knowledge_base/` 当前只有 `报销制度.txt`；学术源通道 `ACADEMIC_MCP_ENABLED` 默认 false，`.env` 未配置。
- **追问时的正确说法**：定位是科研场景，本地库当前只放了示例文档；文献来源依赖外部学术通道。

### 2｜经 MCP 接入学术源

- **代码实际情况**：接入代码存在。`academic.py` 用 `langchain-mcp-adapters` 的 `MultiServerMCPClient`，以 stdio 方式拉起 `arxiv-mcp-server` / `semantic-scholar-mcp` / `pubmed-mcp-server`；但默认开关关闭，`langchain-mcp-adapters` 未安装于当前环境。
- **追问时的正确说法**：MCP 接入已实现，默认关闭，需安装依赖并在 `.env` 打开开关。

### 3｜支持结论溯源

- **代码实际情况**：证据对象带来源结构与原文片段字段；`claim_evidence_map` 只写不读；`raw_text` 未校验；报告引用由 LLM 自行生成，无后置校验。
- **追问时的正确说法**：溯源到证据级（每条 claim 带来源 URL）；报告引用目前依赖模型生成，未做程序校验。

### 4｜产出带引用与置信度

- **代码实际情况**：置信度为 `0.5 + 0.1 × 证据数 − 0.2 × high 问题数`，限制在 [0.3, 1.0]；证据 5 条且无 high 级问题时为 1.0。
- **追问时的正确说法**：该分数是按证据数与遗留问题数线性计算的启发式评分，未经校准，不等同于统计意义上的置信度。

### 5｜Cross-Encoder rerank

- **代码实际情况**：调用远程 SiliconFlow `bge-reranker-v2-m3` HTTP 接口（该模型是 cross-encoder），非本地部署；异常时回退为向量分。
- **追问时的正确说法**：使用 bge-reranker-v2-m3 做精排，通过 HTTP 接口调用，未本地部署。

### 6｜经红队评审与条件路由触发补检索

- **代码实际情况**：`critic → revision` 是 `add_edge` 固定边，Revision 必定执行；红队评审决定补什么（只有缺失类生成检索词），Judge 的路由决定是否进入下一轮。
- **追问时的正确说法**：评审产出补充检索词，Judge 按 high 级问题数与已补轮次决定是否回环。

### 7｜结合 MCP 动态扩展技能

- **代码实际情况**：技能来自 `workspace/office/skills/` 目录扫描（`SKILL.md` 元数据 + 懒加载），与 MCP 无关；MCP 在代码中只用于学术数据源接入。
- **追问时的正确说法**：技能扩展走目录挂载与懒加载；MCP 用于学术数据源接入，两者是不同通道。

### 8｜通过 LLM 熔断提升稳定性

- **代码实际情况**：熔断覆盖 RAG 侧 4 个判定方法；深度调研子图节点走 LangGraph `RetryPolicy`，不进熔断器；升级模型默认未配置。
- **追问时的正确说法**：熔断作用于 RAG 管线的判定类调用；深度调研节点用节点级重试，两者范围不同。
