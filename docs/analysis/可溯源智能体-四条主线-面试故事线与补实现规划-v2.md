## 〇、简历描述

**面向科研场景的可溯源智能体** ｜ AI 应用开发（2026.01 - 2026.03）

基于 LangGraph 构建，聚焦文献调研与知识库 RAG，经 MCP 接入学术源并支持结论溯源。

- 搭建 Planner→Researcher→Critic→Judge 流水线，利用 Send API 并发检索、reducer 汇聚证据避免写冲突，经红队评审与条件路由触发补检索，产出带引用与置信度的结构化报告。

### 按代码原文的描述（简历不动，这一版用于面试对答）

- 调研子图 9 个节点：`planner → scheduler ⇄ researcher → aggregator → review → repair → judge → compiler`。Planner 先按关键词选研究 SOP 再拆任务 DAG；Scheduler 不调模型，只把依赖已满足的任务用 `Send` 派出去；Researcher 检索并登记来源与引文；Aggregator 按引文校验结果推导声明支撑状态；Review 出结构化问题；Repair 按问题局部增删任务；Judge 裁决继续补查还是成文；Compiler 校验引用编号后出报告。并发写入的字段用按 id 合并的 reducer，不用追加。
- 检索走向量 + BM25 双路召回、RRF 融合（k=60）、远程 bge-reranker 精排；多跳问题用 retrieve→reason 循环，每轮把结论压成 1-2 句存入 evidence_state 控制上下文增长。技能来自目录扫描与懒加载，与 MCP 无关。

#### 实体白板（Entity Ledger）设计与运行时机制

1. **核心定位（Recent Conversation + Entity Ledger）**：
   - 解决旧有“150 字自然语言摘要”在长会话（>40回合）中递归压缩导致科研硬约束（如“仅限 2024 年以后”、“限定单麦克风场景”）丢失的问题。
   - 白板是跨回合持久存在的**结构化 Research Canvas**，不承担完整对话记录的替代功能，只保存对后续推理具有持续约束力的状态。

2. **数据模型（Schema）与具体 JSON 形态**：
   依靠 Pydantic 强校验并在 AgentState 中序列化为 JSON 字典：
   - `global_constraints`: 全局硬约束。含 `id`、`content`、`source_turn` (来源回合)、`status`（`active|inactive|removed`）。
   - `resolved_entities`: 明确的实体消歧。含 `id`、`type`（枚举 `paper|method|dataset|model...`）、`name`、`description`、`source_turn`。
   - `pending_questions`: 未决问题。含 `id`、`question`、`source_turn`、`status`（`pending|resolved`）。
   *(注：`source_turn` 溯源字段不仅便于 Debug，也能让系统知晓约束的新旧覆盖关系。)*

3. **LLM 抽取与冲突解决规则**：
   判断信息是否属于这三类**并非依赖死代码或正则，而是交由 LLM 进行大浪淘沙**。触发裁剪时，LLM 按照以下规则增量更新：
   - **用户修改约束**：复用原 `id` 覆写 `content`，禁止出现冲突条目。
   - **用户撤销约束**：变更 `status` 为 `removed`，下游自动物理过滤。
   - **实体消歧**：复用 `id` 更新描述避免冗余；遗留问题解决后置 `resolved`。
   - **抗噪过滤**：严禁闲聊、报错日志或模糊猜测写入，无新信息时原样返回。

4. **加载与全量注入（为何不走向量召回）**：
   - 每段对话加载时，系统从底层的 Checkpointer (SQLite) 中随 `AgentState` 拉取该 JSON。
   - 它是**全量加载过滤后，全量注入 System Prompt**。
   - **坚决不使用向量召回（RAG）**：因为科研硬约束（如“不使用深度学习”）如果在向量空间中与当前具体提问（如“帮我写个排序算法”）相似度不高，极其容易被漏召回，导致模型打破红线。因此它必须作为高权重的“公告栏”显式置顶。

5. **容错降级与职责边界**：
   - **容错**：LLM 输出非法 JSON 失败时，保留旧状态并记录 warning，绝不阻断主流程与历史裁剪。
   - **边界隔离**：`Entity Ledger`（长效约束） / `summary`（兼容过渡摘要） / `evidence_state`（RAG多跳证据集） / `ResearchLedger`（调研子图落盘流水）。

### 主线 1：多智能体调研流水线

**业务背景**：科研调研要对一个问题从多个角度取证并给出可核对来源的结论。单轮检索覆盖不全，任务之间也不独立——不先搞清方法原理，就没法做它和另一个方法的对比。本项目把调研拆成带依赖的任务图，由调度器按依赖分批执行。

**流程**：关键词规则选 SOP（FACT/COMPARISON/MECHANISM/SURVEY，只声明该覆盖哪些维度与拆任务约束，不规定拓扑）→ Planner 拿到 SOP 后拆 3-6 个任务并声明依赖 → Plan Gate（确定性校验 + 最多 2 轮修补 + 1 次 LLM 评审）→ Scheduler 按依赖派发 → Researcher 检索 → Aggregator 合并推导 → Review 出结构化问题 → Repair 局部增删任务 → Judge 裁决。

### 💡 核心面试追问

10. **多 Agent 并发与图状态局部刷新：**
   * **数据防冲突合并 (Reducer 与 1:N 解耦)**：在 `ResearchState` 中弃用 List，采用 Dict 与自定义 Reducer。`sources` 字典按 URL Hash 覆写去重，而 `evidences` 字典按全球唯一 UUID 独立追加存放，保留不同 Agent 对同一网页的不同视角。
   * **“级联回退”机制 (Cascading Reopen)**：Critic 发现事实冲突后，新建补救任务并打上 `{parent}-R{round_no}` 后缀。同时通过向下遍历 DAG，强制把下游节点状态改为 `REOPENED`。
   * **局部增量刷新**：调度器在发车时强行 `continue` 忽略状态为 `SUCCESS` 的历史任务。重跑的下游节点在被唤醒时，拿到的上下文包含了“老证据+新证据”，实现了图状态的局部增量刷新。
11. **调研子图后段（Review -> Repair -> Judge）的拓扑防死锁机制：**
   * **拓扑顺序与职责隔离**：`Review`（化验医生）仅找漏洞开清单，不碰任务流；`Repair`（主治医生）拿到清单后无脑开药下补丁并级联重置；`Judge`（医务处法官）作为终极网关宣判去向。
   * **一票否决的强制熔断（COMPILE_WITH_LIMITATIONS）**：如果陷入“无限挑刺-无限补任务”的死循环（`stagnant_rounds >= 2`），`Judge` 行使一票否决权，强制系统带着残缺数据合成报告以防宕机卡死。
12. **PlanGate V2重构：I/O强制契约+PlanGEN空跑推演：**
   * **结构正确性**：`_check_io_contract` 强校验 `SYNTHESIS` 等节点必须依赖 Provider 节点，直接拦截无证据空跑。
   * **语义充分性**：引入两段式推演：Phase 1 抽取 Checklist（Constraint Agent），Phase 2 模拟空跑比对缺口（Verification Agent），精准抛出 `SCOPE_MISMATCH` 引导 Repair 填补。

### ⚠️ 边界与限制：①闸门只负责判，换不换计划由 Planner 节点决定；②兜底计划是按 SOP required 维度逐个建任务的最小计划，问题针对性弱于模型拆的任务；③`MISSING_FIELD`（任务既无 objective 也无 question）没有可修动作，是唯一稳定触发 REJECT 的问题类型；④依赖仍主要来自 Planner 输出，未声明时按 task_type 规则补（COMPARISON/TREND 依赖 FACT）；⑤`max_revisions` 到上限仍有任务没跑完时按 COMPILE 出报告，未尝试跑完剩余任务。

### 主线 3：RAG 混合召回与 rerank

**业务背景**：本地知识库问答要求召回不漏、排序准。只走向量在关键词不匹配时召回不全，只走 BM25 在语义不匹配时召回不全，所以两路都召回后融合。

### 主线 4：多跳检索循环与决策机制

**业务背景**：跨文档问题需先查 A 才能确定下一步查 B，单轮检索覆盖不到。循环检索的问题是轮数不可控、上下文随轮次累积，以及模型可能反复提同一个检索式或同一个缺口而不收敛。

### 📚 核心架构参考文献与业界对标

在设计本系统的关键卡点与运行时机制时，底层哲学广泛吸取了目前业界 SOTA 框架的成熟经验：

1. **多智能体并发调研与防冲突架构 (Stanford STORM)**
   - **借鉴点**：主线 1 中采用 `Send` API 进行并发 Fan-out 检索时，为解决同一网页不同关注点的合并冲突，采用了严格的 `Source (URL 去重) : Evidence (UUID 分散)` 的一对多解耦结构。
   - **来源对标**：[Stanford STORM (2024)](https://arxiv.org/abs/2402.14207) 在构建 Wikipedia 级别报告时，同样摒弃了粗暴的向量去重，采用 Reference Deduplication（URL 聚合本体 + Quotes 散列支撑），从而保障了严谨的证据溯源与脚标生成。
2. **长效记忆与状态防冲突 (MemGPT)**
   - **借鉴点**：主线 0 的 Entity Ledger 未使用自然语言 Summary 和向量检索（易丢失硬约束），而是采用 Pydantic JSON + UUID 键值对覆写的方式处理用户的改口与冲突。
   - **来源对标**：[MemGPT (Letta)](https://arxiv.org/abs/2310.08560) 的 Core Memory 管理哲学，完全依赖 LLM 作为操作系统，通过工具调用在 JSON 块中精准覆写旧文本，以此解决对话演进中的指令矛盾。
3. **规划闸门的分层校验验证 (PlanGEN / LLM+PDDL)**
   - **借鉴点**：Plan Gate V2 抛弃了由单个 LLM 随意重构整图的做法，改为「纯代码 I/O 强制契约」+「LLM 针对 Checklist 空跑推演」。
   - **来源对标**：[PlanGEN (2025)](https://arxiv.org/abs/2502.16111) 的 Constraint Agent 与 Verification Agent 机制，强调提取实例专属约束并进行模拟验证；同时吸收了 LLM+PDDL 流派中强调的“将 LLM 输出进行符号化强制编译拦截”的思想。
4. **无刚性轮次上限的主循环 (Claude Code CLI)**
   - **借鉴点**：不设置暴力的全局 `Max Steps`，而是任由 LLM `tools_condition` 自然流转结束，防跑飞完全依靠底层的节点熔断与 Entity Ledger 截断。
   - **来源对标**：Anthropic 官方出的 Claude Code 终端 Agent，不设刚性步数墙，依赖上下文滑动与 `/compact` 管理任务深度，保障了解决复杂开发问题的连续推理空间。
