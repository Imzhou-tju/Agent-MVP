# 可溯源智能体 四条主线「面试故事线 + 代码对账 + 补实现方案」

## 〇、简历描述

**面向科研场景的可溯源智能体** ｜ AI 应用开发（2026.01 - 2026.03）

基于 LangGraph 构建，聚焦文献调研与知识库 RAG，经 MCP 接入学术源并支持结论溯源。

- 搭建 Planner→Researcher→Critic→Judge 流水线，利用 Send API 并发检索、reducer 汇聚证据避免写冲突，经红队评审与条件路由触发补检索，产出带引用与置信度的结构化报告。
- 设计向量 + BM25 双路召回、RRF 融合及 Cross-Encoder rerank；针对跨文档问题实现 retrieve-reason 循环，通过结论压缩控制循环风险，结合 MCP 动态扩展技能并通过 LLM 熔断提升稳定性。

### 按代码原文的描述（简历不动，这一版用于面试对答）

- 调研子图 9 个节点：`planner → scheduler ⇄ researcher → aggregator → review → repair → judge → compiler`。Planner 先按关键词选研究 SOP 再拆任务 DAG；Scheduler 不调模型，只把依赖已满足的任务用 `Send` 派出去；Researcher 检索并登记来源与引文；Aggregator 按引文校验结果推导声明支撑状态；Review 出结构化问题；Repair 按问题局部增删任务；Judge 裁决继续补查还是成文；Compiler 校验引用编号后出报告。并发写入的字段用按 id 合并的 reducer，不用追加。
- 检索走向量 + BM25 双路召回、RRF 融合（k=60）、远程 bge-reranker 精排；多跳问题用 retrieve→reason 循环，每轮把结论压成 1-2 句存入 scratchpad 控制上下文增长。技能来自目录扫描与懒加载，与 MCP 无关。

### 主线 1：多智能体调研流水线

**业务背景**：科研调研要对一个问题从多个角度取证并给出可核对来源的结论。单轮检索覆盖不全，任务之间也不独立——不先搞清方法原理，就没法做它和另一个方法的对比。本项目把调研拆成带依赖的任务图，由调度器按依赖分批执行。

**流程**：关键词规则选 SOP（FACT/COMPARISON/MECHANISM/SURVEY，只声明该覆盖哪些维度与拆任务约束，不规定拓扑）→ Planner 拿到 SOP 后拆 3-6 个任务并声明依赖 → Plan Gate（确定性校验 + 最多 2 轮修补 + 1 次 LLM 评审）→ Scheduler 按依赖派发 → Researcher 检索 → Aggregator 合并推导 → Review 出结构化问题 → Repair 局部增删任务 → Judge 裁决。

**追问点**

1. 为什么用 `Send` 而不是 `add_conditional_edges`：后者只能返回单个节点名，给不出 N 个带各自参数的并发实例。
2. 为什么不一次性 fan-out：有依赖的任务要拿到前序结果才能问出有效问题。
3. 为什么并发字段按 id 合并：`operator.add` 是追加，多任务引用同一来源时会登记出重复条目。
4. Repair 为什么不重建整棵树：重开会丢掉已经完成的部分。
5. Judge 为什么不打分：原 `0.5+0.1×证据数−0.2×问题数` 与证据是否通过校验无关。
6. 为什么 SOP 用关键词规则而不是 LLM 选型：零成本、零延迟、结果可复现。
7. 为什么 Critic 只 1 次、修补最多 2 轮：每多一轮就多一次 LLM 成本和把 DAG 改坏的风险，目标是低成本补一遍，不是修到完美。
8. 为什么 SOP 要前置进 Planner：拆任务这一步全靠 LLM prompt，把 SOP 作为 prompt 先验才能从源头约束拆什么，事后校验只能补救已拆错的结果。
9. 量化：`max_revisions` 默认 2；`MAX_REPAIRS=8`；`MAX_VALIDATOR_REPAIR_ROUNDS=2`；Critic 单次最多 3 个 issue。无实测吞吐。

**边界**：①闸门只负责判，换不换计划由 Planner 节点决定；②兜底计划是按 SOP required 维度逐个建任务的最小计划，问题针对性弱于模型拆的任务；③`MISSING_FIELD`（任务既无 objective 也无 question）没有可修动作，是唯一稳定触发 REJECT 的问题类型；④依赖仍主要来自 Planner 输出，未声明时按 task_type 规则补（COMPARISON/TREND 依赖 FACT）；⑤`max_revisions` 到上限仍有任务没跑完时按 COMPILE 出报告，未尝试跑完剩余任务。

```python
# Researcher 并发写：WAL + 可重入锁串行化 —— store.py 的 _write
with self._lock:
    conn.executemany(sql, rows)
    conn.commit()
```

选型：SQLite（WAL）。本项目是单进程本地 Agent，一次调研几十到几百条记录；并发来自同进程内 `Send` 派发的协程，不是多机并发写；项目已依赖 sqlite3，无 ORM、无数据库服务进程。PostgreSQL/MySQL 需要独立服务进程，本场景没有跨进程共享，引入只增加部署成本。

**追问点**

1. 为什么 `source_id` 用内容哈希而不是自增：Researcher 并发执行，自增会给同一 URL 编出不同 id。
2. 为什么 PARTIAL 阈值是 0.6：模型复制引文可能带改写，要求完全相等过严。
3. 为什么声明状态不让模型自评：模型会给自己打高分，支撑状态只取决于证据是否通过校验。
4. 为什么报告用编号而不是 URL：模型抄长 URL 易错，编号由程序映射可机械校验。
5. `UNVERIFIED` 和 `INVALID` 的区别：前者拿不到正文无法判定，后者拿到正文但定位不到。
6. 常量：`PARTIAL_THRESHOLD=0.6`、`MIN_QUOTE_CHARS=8`、`MAX_COMPARE_CHARS=4000`。无实测准确率。

**边界**：校验只比对「本次检索拿到的正文」。网页来源拿到的是搜索摘要而非整页正文，`UNVERIFIED`/`INVALID` 只说明「在拿到的这段文本里定位不到」，不等于原文里不存在；仅摘要的来源即使命中也记 UNVERIFIED（`evidence.py:243`）。本地知识库来源带 `chunk_id`，可定位到具体切片。引文是否真的支持声明由模型在抽取阶段判断，程序不判断。SQLite 同一时刻只允许一个写事务，高并发写会排队，多机共享场景需换 PostgreSQL 并替换 `store.py` 的 SQL 层，上层接口不变。

### 主线 3：RAG 混合召回与 rerank

**业务背景**：本地知识库问答要求召回不漏、排序准。只走向量在关键词不匹配时召回不全，只走 BM25 在语义不匹配时召回不全，所以两路都召回后融合。

**流程**：先评估查询——只在判定不完整时才多查询扩写、判定复杂多跳时才分解子问题，具体查询直接用原 query → 每个查询分别走向量和 BM25 → RRF（k=60）融合 → rerank 精排 → LLM 逐片段判相关过滤 → 评估充分性，不足时改写查询补检索一轮。

| 项 | 做法 | 位置 |
| --- | --- | --- |
| 向量检索 | Chroma 持久化索引，远程 `BAAI/bge-large-zh-v1.5` | `vector_store.py:192-214` |
| BM25 | 语料为子切片，jieba 分词建 `BM25Okapi`，命中后回溯父块去重 | `vector_store.py:216-243` |
| RRF 融合 | 每路按排名累加 `1/(60+rank+1)`，取前 `top_k*2` | `service.py:170-181` |
| rerank | 远程 `bge-reranker-v2-m3` HTTP，写回 `rerank_score`，异常回退向量分 | `service.py:500-533` |
| 片段过滤 | LLM 逐片段判相关，不相关丢弃 | `service.py:183-224` |
| 充分性评估 | 判定不足则改写查询补检索一轮 | `service.py:226-272` |

```python
# RRF 按排名累加，k=60 —— service.py:170-181
rrf_k = 60
merged[doc_id]['rrf_score'] += 1.0 / (rrf_k + rank + 1)
final_list = sorted(merged.values(), key=lambda x: x.get('rrf_score', 0), reverse=True)
return final_list[:search_top_k * 2]

# BM25 命中子切片后回溯父块去重 —— vector_store.py:232-240

if parent_chunk_id in seen_parents:
    continue
seen_parents.add(parent_chunk_id)

# rerank 异常回退向量分 —— service.py:529-533
except Exception as e:
    for doc in documents:
        doc["rerank_score"] = doc.get("score", 0.0)
        doc["rerank_status"] = "FALLBACK"
```

**RRF 算例**：文档 A 在向量路排第 0、在 BM25 路排第 2 → `1/61 + 1/63 = 0.0325`；文档 B 只在向量路命中排第 1 → `1/62 = 0.0161`。A 排前。两路分数不可比（向量是余弦、BM25 是词频统计），用排名才能放在同一个量级上相加。

**追问点**

1. 为什么默认不扩写：具体查询被扩写会引入无关词，降低匹配分。
2. 为什么 RRF 用排名不用分数：两路分数不可比，排名可归一化。
3. BM25 为什么绑子切片再回溯父块：子切片匹配准，父块给完整上下文。
4. rerank 失败怎么办：回退向量分，结果仍可用但排序质量下降。
5. 量化：`RAG_INITIAL_TOP_K=15`、`RAG_TOP_K=4`、`RAG_MAX_ITERS=4`。无实测召回率。

**边界**：rerank 依赖远程接口，异常时改用向量分排序；没有召回评测集，无法给出召回率数字。

### 主线 4：多跳检索循环与 LLM 熔断

**业务背景**：跨文档问题需先查 A 才能确定下一步查 B，单轮检索覆盖不到。循环检索的问题是轮数不可控、上下文随轮次累积。

**流程**：循环体是「检索一轮 → 结果压成 1-2 句带来源的结论存入 scratchpad → 推理还缺什么并生成下一子问题」。scratchpad 只存压缩后的结论不存原文，上下文不随轮次线性增长。终止三个条件：判定已充分、提不出新子问题、缺口描述连续两轮不变。

| 项 | 做法 | 位置 |
| --- | --- | --- |
| 循环主体 | `search_iterative`，每轮检索 + 压缩 + 推理下一子问题 | `service.py:430-498` |
| 结论压缩 | 单轮结果压成 1-2 句带来源的结论 | `service.py:313` |
| 三个终止条件 | 判定已充分 / 提不出新子问题 / 缺口描述连续两轮不变 | `service.py:475-487` |
| 熔断与死信 | 重试 → 计失败 → 升级模型 → 死信入队 → 返回降级值 | `rag/reliability.py:182-239` |
| 调研侧收口 | planner/researcher/review/compiler/semantic 的模型调用统一走 `reliable_llm_call` | `research/reliability.py:62` |
| 节点级重试 | LangGraph `RetryPolicy`：planner/review/compiler 3 次，researcher 2 次 | `graph.py:44-55` |

```python
# 三个终止条件 —— service.py:475-487

if not decision["next_sub_question"]:  break   # 提不出新子问题

    try:    return stronger_fn()
    except Exception as e:  last_error = e

```

**调用次数算例**：单轮 `search_agentic` 最多 4 次判定调用（查询评估、片段过滤、充分性判定，判定不足时改写补检索会再评估一次）+ 1 次结论压缩；`search_iterative` 最多 `RAG_MAX_ITERS=4` 轮，加最后 1 次综合 → 单次多跳检索的 LLM 调用上限是 4×5+1 = 21 次。这是调用次数，不是耗时，也没有实测。

**追问点**

1. 为什么 scratchpad 存结论而不是原文：原文随轮次累积会撑大输入。
2. 为什么需要「缺口连续不变」这个条件：前两个条件挡不住模型反复提同一个缺口。
3. 熔断覆盖哪些调用：判定类调用（RAG 侧 6 个方法 + 调研侧 5 个节点）走 `llm_call_with_reliability`；节点级另有一层 `RetryPolicy`，两层叠加。
4. 熔断只保证「调用能不能成功返回」，不保证内容对不对；失败返回 `fallback`（如空串），由调用方已有的解析兜底逻辑处理。

**边界**：升级模型默认关闭（`RAG_LLM_ESCALATION_MODEL` 为空）；死信队列只落记录，不自动重试。
